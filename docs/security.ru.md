# Vinaire — безопасность

[English](./security.md) · **Русский**

Это итог аудита Phase 36: краткая модель угроз, свойства, которые были **проверены** (и как,
чтобы вы могли проверить их снова), и оставшиеся риски. Это набор утверждений, поддающихся
проверке, а не гарантия отсутствия уязвимостей: автоматические сканеры не находят логических
ошибок, поэтому критичные пути ниже нужно отдать на независимый ручной разбор, прежде чем
Vinaire станет доступен извне доверенной сети.

## Что такое Vinaire с точки зрения безопасности

Vinaire — веб-интерфейс перед одним или несколькими кластерами Kubernetes. Почти всё, что он
делает, выполняется **от имени вошедшего пользователя**: собственный токен Kubernetes
пользователя (вставленный токен ServiceAccount или OIDC-идентичность) хранится на сервере за
непрозрачной cookie сессии и используется для каждого вызова, так что что именно человек
видит и может делать, решает RBAC кластера, а не Vinaire. Исключения намеренные и перечислены
в `AGENTS.md`:

- информеры живых обновлений читают pods, deployments, statefulsets, daemonsets, jobs и nodes
  с *собственным* ServiceAccount Vinaire (и каждое событие перед отправкой проверяется по RBAC
  подключённого пользователя);
- собственная конфигурация Vinaire — реестр кластеров и источники GitOps, — которая содержит
  учётные данные, хранится в зашифрованном виде и меняется только с правом, которое выдаёт
  кластер (см. ниже);
- нативная синхронизация GitOps, которая работает, когда никто не вошёл, и потому применяет
  манифесты от имени ServiceAccount, токен которого пользователь передал для этого источника.

**Поскольку Vinaire хранит учётные данные каждого зарегистрированного в нём кластера, это
единая точка с доступом ко всем им.** Относитесь к нему как к бастиону.

### Активы

| Актив | Где находится | Защита |
|---|---|---|
| Токен Kubernetes пользователя | память сервера, на время сессии (≤ 12 ч) | непрозрачный 256-битный id сессии в cookie HttpOnly+Secure+SameSite=Strict; никогда не попадает в лог, URL или ответ |
| Учётные данные зарегистрированных кластеров (токены, kubeconfig) | Secret (в кластере) или файл (`VINAIRE_DATA_DIR`) | AES-256-GCM; ключ из `CLUSTER_STORE_KEY` или отдельного Secret / файла 0600; ротация возможна |
| Токены git/ServiceAccount для GitOps | то же зашифрованное хранилище | то же; отказ, если хранилище не зашифровано |
| SSH-пароли/ключи для установки | память, на время одной задачи | обёрнуты в `Secret` (печатается `[REDACTED]`), вычищаются из каждой строки лога, на диск не пишутся |
| Значения Secret | кластер | только через аудируемый endpoint `reveal`, от имени вызывающего |

### Кто может атаковать и откуда

| Актор | Что может попробовать | Основная защита |
|---|---|---|
| Любой в сети | подбор входа, засорение сессий, сканирование | токен проверяется по кластеру до создания сессии; ограничитель входа (по адресу и по токену, с нарастающей паузой); лимит сессий |
| Вошедший пользователь с низкими правами | увидеть чужие namespace; добавить кластер; воспользоваться идентичностью Vinaire | каждый вызов идёт от его имени; поток фильтруется по каждому событию; изменения самого Vinaire требуют права `vinaire.io` |
| Вредоносный сайт, который открыл пользователь | CSRF; открытие WebSocket с cookie пользователя | SameSite=Strict, проверка `Origin`/`Sec-Fetch-Site` на каждом изменяющем запросе и каждом рукопожатии WebSocket |
| Содержимое из кластера (имена подов, метки, текст событий, строки логов) | XSS | выводится только как текст; ESLint запрещает HTML-приёмники; CSP не допускает inline-скрипты |
| Враждебный Helm-репозиторий / git-репозиторий / реестр | поставить вредоносное; SSRF; огромные загрузки | репозитории только из конфигурации оператора; проверка digest чарта; защищённый dialer; ограничения размера и количества |
| Скомпрометированный под Vinaire | читать Secret других namespace; писать | минимальный ServiceAccount (без Secret и без записи), укреплённый контейнер, NetworkPolicy (по желанию) |

## Выдача прав администраторам

Изменение самого Vinaire — не действие Kubernetes, поэтому ни одно правило Kubernetes его не
покрывает. Вместо этого Vinaire спрашивает у кластера, может ли вошедший пользователь
`create`/`update`/`delete` над *виртуальными* ресурсами `clusters.vinaire.io` и
`gitops.vinaire.io` (в кластере их нет; это лишь имена для права) на своём кластере по
умолчанию. Чарт создаёт роли без привязок:

```bash
# смотреть и действовать (те, кто пользуется Vinaire)
kubectl create clusterrolebinding alice-viewer --clusterrole=<fullname>-viewer --user=alice
# менять сам Vinaire (тот, кто им администрирует)
kubectl create clusterrolebinding alice-admin  --clusterrole=<fullname>-admin  --user=alice
```

`AUTH_MODE=disabled` (одноразовый локальный кластер, входа нет вообще) эту проверку
пропускает.

## Как эксплуатировать безопасно

- **Не выставляйте Vinaire напрямую в интернет.** Ходите к нему через VPN (WireGuard,
  NetBird, Tailscale). Если он обязан быть публичным — только за HTTPS с настоящим
  сертификатом (cert-manager), с `cookie.secure: true` и, лучше, за дополнительным
  аутентифицирующим прокси.
- Включайте `trustForwardedFor: true` **только** если прокси, которым вы управляете,
  проставляет `X-Forwarded-For`; иначе ограничитель входа считает адрес прокси за всех.
- Держите `CLUSTER_STORE_KEY` вне репозитория и образа; ротируйте, задав новый ключ и перенеся
  старый в `CLUSTER_STORE_KEY_PREVIOUS`, затем один раз перезапустите.
- Выдавайте роль `-admin` как можно меньшему числу людей: она может зарегистрировать кластер,
  учётные данные которого Vinaire потом будет хранить.
- Включите `networkPolicy.enabled`, если ваш CNI её применяет (входящее только от ingress,
  исходящее только к DNS, 443/6443 и — если ставите по SSH — 22, никогда не на адрес
  метаданных), и сохраняйте журнал аудита: либо включите `audit.persistence.enabled: true`
  (том под файл, см. «Как сохранить журнал аудита» ниже), либо отправляйте stdout контейнера
  в вашу систему логов — по умолчанию файл аудита лежит на `emptyDir` и теряется при замене пода.
- `PROVISION_ALLOW_INSECURE` и `GITOPS_ALLOW_INSECURE_GIT` существуют только для локальной
  разработки.

## Как сохранить журнал аудита

Каждое аудируемое действие пишется дважды: JSON-строкой в файл аудита (`AUDIT_LOG_PATH`, `/audit/audit.log`, ротация по
10 МБ, хранится пять файлов; его читает страница «Audit log») и строкой в лог контейнера (stdout).

- **Файл** по умолчанию лежит на `emptyDir`: он переживает перезапуск контейнера и теряется при замене пода.
  `audit.persistence.enabled: true` кладёт его на PersistentVolumeClaim (`audit.persistence.size`, `storageClass` либо свой
  claim в `existingClaim`). Том ReadWriteOnce с одним писателем, поэтому нужен `replicaCount: 1`; Deployment при этом
  использует стратегию `Recreate`, а claim **сохраняется** при `helm uninstall` (это запись о том, что делали, — удалите его
  сами, если он не нужен).
- **stdout** — то, что по умолчанию читает сборщик логов (Promtail/Grafana Alloy, Fluent Bit, агент ноды), и это работает
  с несколькими репликами. Каждое аудируемое действие — строка с сообщением `audited action` и полями `action`, `namespace`,
  `name`, `identity`, `remoteAddr` и подробностями действия — без значений секретов. В Loki, например:
  `{namespace="vinaire"} |= "audited action"`; чтобы оставить только изменения, отфильтруйте по `action`. Отправляйте
  его туда, где люди, чьи действия записаны, не могут его править.

Одно другому не мешает: файл на томе — для страницы «Audit log», stdout — для хранения и оповещений.

## Известные остаточные риски

- **Одно хранилище учётных данных.** Компрометация Vinaire раскрывает каждый зарегистрированный кластер.
  Это неотъемлемо для консоли с несколькими кластерами; смягчается пунктами выше, мастер-ключом в Vault
  (`keyProvider.type: vault`), короткоживущими токенами кластеров и их заменой до истечения.
- **По умолчанию сессии в памяти.** При одной реплике перезапуск разлогинивает всех. Включите
  `sessions.store: secret` (по умолчанию для нескольких реплик), чтобы хранить их запечатанными в общем Secret.
  Сессия хранит настоящий токен Kubernetes пользователя до 12 ч в любом случае; ограничитель входа и запущенные
  установки остаются на своей реплике.
- **Проверка TLS пропускается в трёх проверенных местах:** HTTPS-под через проброс порта (его
  сертификат обычно самоподписанный; соединение — туннель через API Kubernetes), проба
  идентичности локально обнаруженного кластера (ничего не отправляется) и кластер, добавленный
  с токеном, но без CA-сертификата (интерфейс говорит об этом и спрашивает).
- **CSP сохраняет `style-src 'unsafe-inline'`**, потому что интерфейс задаёт атрибуты style, а
  Monaco внедряет стили. Скрипты ограничены хешами.
- **`npm audit` сообщает о двух низких предупреждениях** по DOMPurify внутри `monaco-editor`
  (исправление требует мажорного обновления с ломающими изменениями). Редакторы показывают
  только собственный YAML пользователя; недоверенный markdown они не рендерят.
- **Фильтр потока работает по виду и namespace**, на основе права `list`. RBAC тоньше этого
  (`resourceNames`, селекторы меток) для строки не вычисляется; отозванное право начинает
  действовать на открытом потоке в течение 10 с.
- **Любой, кто может прочитать Secret в кластере, может показать его** через Vinaire
  (аудируется). Vinaire не добавляет ограничений сверх RBAC.
- **SSH-установка по замыслу выполняет команды от root на сервере.** Она закрыта (create
  `nodes`, а для создания/импорта кластера ещё `clusters.vinaire.io`), только по HTTPS, с
  закреплением host key и аудитом.
- **Реплика, умершая посреди продления, может стоить человеку сессии.** Продления разных реплик разведены арендой, которая сама истекает примерно через 40 секунд, но если реплика умерла после того, как Keycloak ротировал refresh-токен, и до того, как её сохранила, новый токен потерян, и следующее продление завершит сессию — человеку придётся войти снова. Доступа это никому не даёт.
- **Локально не проверено:** сканирование образа Trivy, базовый прогон OWASP ZAP и
  *применение* NetworkPolicy (политика рендерится и принимается API-сервером). Они есть в
  workflow `Security`. Режим Argo CD проверялся только на подставной CRD.
- **История:** в истории git есть один просроченный bootstrap-токен kubeadm из одноразового
  тестового контейнера (коммит `1bef880`). Он мёртв (токены kubeadm живут 24 ч, а того
  кластера больше нет).

## Рекомендуется до выхода Vinaire за пределы доверенной сети

Независимый ручной разбор: входа и сессий (`internal/authn`), exec
(`internal/stream/exec.go`), reveal Secret, применения YAML, SSH-установки
(`internal/provision`) и хранения kubeconfig/реестра (`internal/clusters`) — мест, где
логическая ошибка важнее всего и где ни один сканер не смотрит.
