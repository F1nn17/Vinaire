# Чего не хватает Vinaire по сравнению с Headlamp и Rancher

Анализ после правок из `docs/ui-backlog.md`. Составлен по **моим знаниям о двух продуктах**
(Headlamp — веб-UI и десктоп-приложение CNCF/Kubernetes SIG UI; Rancher — платформа управления
множеством кластеров от SUSE), **а не по сверке с их свежими версиями**: перед тем как заводить
фазы, стоит открыть оба и пройти по списку — особенно пункты, помеченные «проверить». Состояние
самого Vinaire — по коду и `ROADMAP.md` (фазы 0–38).

Приоритеты: **P1** — без этого пользователи уйдут на kubectl или другой UI; **P2** — заметно
улучшает жизнь; **P3** — приятное дополнение / нишевое. Размер: S (≤ неделя), M, L.

Что у Vinaire уже сильнее или не хуже: аудит каждого действия и жёсткая модель прав «от имени
пользователя» (Phase 36), Marketplace с проверкой прав и прогрессом, GitOps двух видов, создание
кластеров и нод по SSH (k3s, kubeadm), порт-форвард в браузере, форма + YAML + dry-run/diff.

## 1. Сравнение с Headlamp

| Область | Headlamp | Vinaire | Разрыв |
| --- | --- | --- | --- |
| Список ресурсов | Все встроенные виды: Workloads (Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs), Storage, Network, Config (ConfigMaps, Secrets, HPA, PDB, ResourceQuota, LimitRange, PriorityClass…), Cluster (Nodes, Namespaces, Events, CRDs) | Pods, Deployments, StatefulSets, DaemonSets, Jobs, Services, Ingress/Gateway, PVC/PV/StorageClass, ConfigMaps, Secrets, Namespaces, Nodes, RBAC (чтение), CRD | **CronJobs, ReplicaSets, HPA, PodDisruptionBudgets, NetworkPolicies, PriorityClass, Leases, Endpoints/EndpointSlices, ServiceAccounts (страница), Events как отдельный список** |
| Универсальный просмотр любых ресурсов | Через CRD-страницы; единый шаблон списка/деталей | Custom Resources (Phase 15) только для CRD | Нет универсального «любой ресурс по GVK» (в т. ч. встроенные виды без своей страницы) |
| Редактор YAML | Monaco, редактирование, создание | Monaco + dry-run + diff + оптимистичная блокировка (сильнее) | — |
| Логи | Потоковые, мульти-контейнер, скачивание, фильтр | Live + поиск + история (Loki) | Скачать лог файлом; логи сразу всех подов Deployment/StatefulSet; «предыдущий контейнер» (`--previous`) — **проверить** |
| Терминал | exec в под | Есть (Phase 5) | Терминал на ноду (debug-под / `kubectl debug`) |
| Метрики | Через metrics-server и плагин Prometheus | Metrics-панель (Phase 32) + Requests & Limits | Установка стека одной кнопкой — Phase 37 (запланирована) |
| Плагины / расширяемость | Плагины на JS, каталог плагинов, смена тем | Нет | **P3**: публичного API расширений нет и в ближайшее время не нужен |
| Темы | Светлая и тёмная | Только тёмная (по решению проекта) | P3; светлая тема — только если попросят (AGENTS.md) |
| Десктоп-приложение | Есть (Electron) | Нет — веб/Helm | P3 |
| Мультикластер | Через kubeconfig, переключатель | Реестр кластеров, SSH, обнаружение | — |
| Поиск | Глобальный поиск по ресурсам | ⌘K (Phase 20) | — |
| Карта связей | Map view (граф) | Topology (Phase 7) | Расширить на ресурсы за пределами workload→pod→node — P3 |
| Сортировка/фильтры таблиц | Сортировка по колонкам, фильтры по namespace/метке, выбор колонок, пагинация | Базовые таблицы, фильтр по namespace в части страниц | **P1/P2**: единые сортировка, фильтр по меткам, выбор колонок, сохранение вида — на всех списках |
| Массовые действия | Нет (в основном) | Нет | — |
| i18n | Много языков | Смешанный русский/английский в интерфейсе | **P2**: определиться с языком интерфейса (сейчас справка русская, остальное английское) |

## 2. Сравнение с Rancher

| Область | Rancher | Vinaire | Разрыв |
| --- | --- | --- | --- |
| Cluster Explorer | Полный обзор любого кластера: workloads, service discovery, storage, policy, «More Resources» (все API-группы) | Основные виды (см. выше) | Нет «More Resources» — доступа ко всем API-группам кластера через discovery (**P1**, M) |
| Создание кластеров | RKE2/K3s на своих узлах, облака (EKS/GKE/AKS), Harvester, vSphere — через node drivers и cloud credentials | K3s и kubeadm по SSH (Phase 34/35) | Облачные провайдеры и node drivers — **P3** (большая отдельная тема, L); обновление версии кластера (upgrade k3s/kubeadm) и **удаление ноды (drain + remove)** — **P1/P2** (M) |
| Жизненный цикл узлов | Drain/cordon/uncordon, taints, labels, замена | Добавление и reset по SSH | **Cordon / uncordon / drain, редактирование labels и taints** — **P1** (S–M); upgrade — P2 |
| Apps / Marketplace | Каталог Helm (Rancher Charts, Partners, свои репозитории), UI значений, обновление | Marketplace (Phase 28): много репозиториев, OCI, прогресс, предпроверка прав | Формы значений по `values.schema.json` вместо сырого YAML — **P2** (M); добавление **своего репозитория из UI** (сейчас только конфиг оператора — осознанное решение безопасности, пересмотреть) — P3 |
| RBAC и пользователи | Глобальные роли, проекты, роли кластера, внешние провайдеры (AD/LDAP/GitHub/Keycloak/Okta/SAML), привязка пользователей и групп через UI | RBAC только для просмотра; вход токеном/OIDC; роли выдаёт администратор через kubectl | **Управление RBAC из UI** (создать Role/RoleBinding, привязать пользователя/группу) — **P1/P2** (M), по правилам AGENTS.md — отдельное решение, т. к. новая запись; «Что может пользователь X» (can-i-аудит) — P2 |
| Проекты / мультиарендность | Project = группа namespace с квотами и ролями | Namespaces с квотами (Phase 27) | Группировка namespace в «проекты» — P3 |
| Мониторинг | Встроенный Prometheus/Grafana (rancher-monitoring), алерты, дашборды | Интеграция с Prometheus/Loki/Alertmanager (Phase 16/32), метрики одной кнопкой — Phase 37 | Дашборды-конструктор — P3; в Phase 37 нужно проверить права и ресурсы |
| Логирование | Banzai/Logging Operator | Loki-поиск | Установка стека логов одной кнопкой (аналог Phase 37 для Loki) — **P2** (M) |
| Безопасность и политики | CIS-сканы, Kubewarden/OPA Gatekeeper, NetworkPolicy-редактор, Pod Security Admission | NetworkPolicy — только через YAML, сканов нет | **NetworkPolicy: список и форма** — **P2** (S/M); PSA-метки на namespace в форме — P2; CIS-скан (kube-bench) — P3 |
| Резервные копии | Backup Operator, etcd snapshots | Нет | Установка Velero через Marketplace есть (чарт), UI для расписаний/восстановления — **P3**; etcd snapshot для k3s/kubeadm — P2 |
| GitOps | Fleet (встроен) | Native + Argo CD (Phase 29) | Мультикластерные развёртывания (один репозиторий → много кластеров), приоритет — P3 |
| Аудит | Audit log кластера | Аудит каждого действия Vinaire (JSON, `AUDIT_LOG_PATH`) | **Просмотр аудита в UI** (фильтры по пользователю/действию/времени) — **P2** (M): сейчас только файл/stdout |
| Горячие точки эксплуатации | Alerts, Events на уровне кластера, уведомления | Колокольчик алертов, события пода | **Страница Events** (по всему кластеру, с фильтрами, предупреждения) — **P1** (S) |
| Масштабирование и HPA | Редактор HPA, VPA | Scale вручную (Phase 33) | **HPA: просмотр и форма** — P2 (S); рекомендации по requests/limits (на основе usage) — P2 |
| Удобство | Глобальные настройки, брендинг, SSO, подсказки | Справка в Settings | Брендинг/настройки — P3 |

## 3. Что стоит завести фазами (рекомендуемый порядок)

1. **Phase A — «Все ресурсы» (P1, M) — ✅ сделано (ROADMAP Phase 39).** Универсальная страница по результатам API discovery
   (аналог «More Resources»): любая группа/вид, список, детали, YAML. Плюс недостающие встроенные
   страницы: **CronJobs, ReplicaSets, HPA, PDB, NetworkPolicy, ServiceAccount, Events**.
   Закрывает самый заметный разрыв с обоими продуктами.
2. **Phase B — Жизненный цикл узлов (P1, M) — ✅ сделано (ROADMAP Phase 40).** Cordon / uncordon / drain (с учётом PDB),
   редактирование labels и taints, удаление ноды из кластера. Это новые *записи* → по AGENTS.md
   сначала отдельное решение и пункт в списке разрешённых записей.
3. **Phase C — Таблицы: сортировка, фильтры, колонки (P1/P2, S–M) — ✅ сделано (ROADMAP Phase 41).** Единый `DataTable` с
   сортировкой, фильтром по меткам и namespace, выбором колонок, сохранением в URL.
4. **Phase D — Просмотр аудита в UI (P2, M) — ✅ сделано (ROADMAP Phase 42).** Фильтры по пользователю, действию, времени;
   только для тех, у кого есть право `requireVinaireRight`.
5. **Phase E — Управление доступом из UI (P2, M).** Role/RoleBinding/ClusterRoleBinding: создать,
   привязать пользователя/ServiceAccount, «что может X» (через SelfSubjectAccessReview/
   SubjectAccessReview). Тоже новая запись — отдельное решение.
6. **Phase F — Формы значений Helm (P2, M) — ✅ сделано (ROADMAP Phase 43).** Форма по `values.schema.json` чарта (где он есть)
   вместе с YAML-режимом, как у Create (Phase 31).
7. **Phase G — Стек логов одной кнопкой (P2, M).** По образцу Phase 37 (Loki + сборщик).
8. **Phase H — Язык интерфейса (P2, S–M).** Выбрать один язык по умолчанию и перевод/переключатель;
   сейчас смесь.
9. **P3 — по запросу:** обновление версии кластера, облачные провайдеры, проекты, сканы CIS,
   плагины, светлая тема, десктоп-приложение.

## 4. Что сознательно **не** копировать

- **Широкие права Vinaire от своего имени** (как у части установок Rancher): модель «действуем как
  пользователь, права решает Kubernetes» — сильная сторона; не заменять собственным слоем политик
  (AGENTS.md).
- **Добавление любых репозиториев Helm прямо из запроса**: репозитории — только из конфигурации
  оператора (Phase 28/36). Если нужно из UI — через `requireVinaireRight` и с теми же ограничениями
  (https, без внутренних адресов, контрольные суммы), как отдельное решение.
- **Встроенные плагины с произвольным JS**: расширяет поверхность атаки (CSP, Phase 36).
