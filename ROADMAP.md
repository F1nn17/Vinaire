# Roadmap

Vinaire ships in **vertical slices**, not horizontal layers. Every phase below
is one end-to-end feature — a real backend endpoint wired to the real frontend
screen that already exists (built against mock data) — not "all the backend"
followed by "all the frontend." Each phase ends with something you can click
through in a browser against a local k3d cluster, and a concrete **Definition
of done** you can run yourself to confirm it actually works before moving on.

Phases are ordered read-only → live → interactive → write → secured →
multi-cluster on purpose. The order is fixed; scope inside a phase can flex.

Current state this plan builds on: `/frontend` is a fully built UI on mock
data (Next.js + TypeScript + Tailwind, SWR-based data layer with a clean
`lib/api/*` seam already in place for swapping mocks for real fetches), and
`/backend` is a Go + chi + client-go skeleton with one working endpoint
(`GET /healthz`) and a read-only Kubernetes client stub.

## Notes on the current repo (read before starting Phase 0)

A few things surfaced while re-reading `/frontend`, `/backend`, and
`AGENTS.md` against this plan. None of them require changing README.md or
AGENTS.md right now — they're either already consistent, or gaps to close
*as part of* the phase where they start to matter. Flagging them here so
they don't get lost.

- **CORS target port is `3100`, not `3000`.** The frontend was moved off
  Next.js's default port earlier (port 3000 is taken by another local tool
  on this machine) — `frontend/package.json`'s `dev`/`start` scripts already
  run on `-p 3100`, and README.md already documents this. Phase 0's CORS
  config below uses `3100` accordingly.
- **Pod/Deployment detail routes are name-only — this will break on real
  data.** `src/app/(shell)/workloads/pods/[name]/page.tsx` and the
  `deployments/[name]` equivalent, plus `getPod(name)` / `getDeployment(name)`
  in `lib/api/workloads.ts`, key purely by resource name. That's fine for
  mock data (names happen to be globally unique), but two different
  namespaces can absolutely have a pod named the same thing on a real
  cluster. **Fix this at the Phase 1 boundary**, before real data starts
  flowing: routes become `/workloads/pods/[namespace]/[name]` (same for
  deployments), and the `WorkloadRow.href` values generated by the backend
  already encode the right path. Doing it in Phase 1 means Phase 3 doesn't
  have to re-touch routing.
- **`internal/k8s` staying fully read-only holds through Phase 8, then
  Phase 9 deliberately narrows — not bends — that rule.** Phases 0–8 never
  add a write verb. Phase 9's Restart/Delete/Rollback actions do add write
  verbs to `internal/k8s`, directly against the live cluster — this
  supersedes the GitOps-PR design this phase originally had. It was an
  explicit decision, not a quiet exception: AGENTS.md's core rule has been
  updated to match (it now names exactly these three actions as the only
  allowed writes, everything else stays read-only). If you're reading this
  note without also having read AGENTS.md's current version, read that
  first — it's the source of truth for what's actually allowed to write.
- **`AGENTS.md`'s repository-structure tree will go stale incrementally**,
  not all at once — phases 1–11 each add a backend package
  (`internal/api`, `internal/stream`, `internal/gitops`, `internal/auth`,
  `internal/cluster`, ...) that doesn't exist yet. Recommend updating that
  tree phase-by-phase, in the same PR as the phase that introduces the new
  package, rather than speculatively now.
- **README.md's Prerequisites section doesn't yet say how to stand up the
  local k3d cluster** Phase 1's Definition of done assumes exists (it only
  says "a reachable cluster... k3d is the intended dev target"). Worth
  adding a concrete `k3d cluster create vinaire-dev` snippet — good scope
  for the Phase 1 PR, since that's the first phase that actually needs one
  running.
- **Data-fetching library: already decided.** `frontend` already uses
  [SWR](https://swr.vercel.app/), installed and wired through
  `lib/hooks/*.ts`. Keeping it rather than introducing React Query — SWR's
  API is a better fit for this app's shape (mostly key-based GETs, no
  complex mutation/cache-invalidation graphs), it's smaller, and it's from
  the same team as Next.js. Phase 0 below documents this as a confirmed
  decision, not an open question.
- **⚠ Security-sequencing flag on Phase 5 — resolved, accepted.** Terminal/
  exec lets you run arbitrary commands inside a real pod, and it shipped
  *before* Phase 10 (auth). Decision made explicitly (not a default/
  oversight): accept the exposure since this only ever runs against a
  local-only dev cluster right now. No feature flag added. **Revisit this
  before the backend is ever reachable by anyone but the developer running
  it** — that's what Phase 10 is for.

## Phase 0 — Dev infrastructure ✅ done

**Goal:** both apps boot cleanly, talk to each other, and prove it in the UI.

**Backend**
- New `internal/config` package: load `PORT` (default `8080`), `KUBECONFIG`
  (already read ad hoc in `internal/k8s/client.go` — centralize it here),
  and `CORS_ALLOWED_ORIGINS` (default `http://localhost:3100`) from env with
  sane defaults, so nothing *requires* env vars to run locally.
- Replace `log` with `log/slog` (stdlib since Go 1.21 — **zero new
  dependency**) for structured logging; log every request's method/path/
  status/duration and the CORS origin on startup.
- CORS middleware restricted to the configured origin(s) — needed the
  moment the frontend makes a real cross-origin fetch in Phase 1.
- Graceful shutdown: `http.Server` combined with `signal.NotifyContext`
  (`SIGINT`, `SIGTERM`) and `Shutdown(ctx)`. Doesn't matter much yet, but
  Phase 2's informers need clean teardown and it's cheaper to build the
  habit now than retrofit it.

**Frontend**
- `lib/api/config.ts` already exports `API_BASE` from
  `NEXT_PUBLIC_API_BASE` — add a small `apiFetch<T>(path): Promise<T>`
  wrapper next to it (JSON parsing, non-2xx → thrown `ApiError`) that every
  real `lib/api/*.ts` function will call starting Phase 1. No behavior
  change yet — the mock functions keep returning mock data.
- Add a minimal connection-status indicator (a small dot + label is enough
  — reuse the `StatusDot` component) somewhere in the shell, e.g. next to
  the alerts bell in `Topbar`, backed by a new `useHealthz()` SWR hook
  polling `GET /healthz` every few seconds.

**New dependencies**
- `go.mod`: `github.com/go-chi/cors`
- `package.json`: none (SWR already installed)

**Complexity:** S

**Risks to check early**
- None operationally — this phase is plumbing. The one thing worth
  double-checking: the CORS origin literally has to match `http://localhost:3100`
  exactly (scheme + host + port), or the browser silently blocks the
  Phase 1 fetch with an opaque CORS error that's annoying to debug blind.

**Definition of done**
```
npm run dev   # from repo root — starts backend :8080 and frontend :3100
```
Open the frontend: the status indicator shows "backend: connected" once
`/healthz` resolves. Stop the backend process (Ctrl+C on it alone, or kill
`:8080`): within one poll interval the indicator flips to "unreachable" and
the rest of the UI keeps working (no crash, no white screen).

## Phase 1 — Pods & Deployments (read-only, `List()`, no live updates) ✅ done

**Goal:** Workloads' Deployments and Pods tabs show your real cluster.

**Backend**
- `internal/k8s`: `ListPods(ctx, namespace string) ([]corev1.Pod, error)` and
  `ListDeployments(ctx, namespace string) ([]appsv1.Deployment, error)` via
  `clientset.CoreV1().Pods(ns).List()` / `clientset.AppsV1().Deployments(ns).List()`.
  Empty `namespace` = all namespaces (`""` in the K8s API already means
  cluster-wide list).
- New `internal/api` package (handlers), wired up in `main.go`:
  `GET /api/v1/pods?namespace=`, `GET /api/v1/deployments?namespace=`.
  Response shape matches the frontend's existing `WorkloadRow` type exactly
  (`name`, `namespace`, `ready`, `status`, `statusColor`, `restarts`, `age`,
  `href`) — the mapping/status-derivation logic (pod phase → color,
  ready-replicas-vs-desired → Healthy/Degraded) is the actual business logic
  in this phase, not the HTTP plumbing around it.
- **Do the same for StatefulSets/DaemonSets/Jobs in this phase too** — not
  in the original phase text, but it's the identical `List()` + map pattern
  with zero extra design cost once Pods/Deployments are done, and it avoids
  the Workloads page having 2 real tabs and 3 permanently-mock tabs.
- **Apply the namespace-in-route fix from the notes above**: `href` values
  the backend generates for each row are `/workloads/pods/{namespace}/{name}`
  and `/workloads/deployments/{namespace}/{name}`.

**Frontend**
- Update the pod/deployment detail routes to
  `[namespace]/[name]` (currently `[name]` only).
- `lib/api/workloads.ts`: `getWorkloads(kind)` calls
  `apiFetch(`/api/v1/${kind}?namespace=${ns}`)` instead of returning
  `workloadsMock[kind]`. `lib/hooks/useWorkloads.ts` and every component
  consuming it (`WorkloadsPage`, `DataTable`) need **zero changes** — this
  is exactly the seam the mock-data layer was built for.
- Namespace filter: reuse the existing (currently decorative) namespace
  affordance, or add a simple `<select>` for now — full namespace-context
  plumbing isn't needed until Phase 7.

**New dependencies**
- `go.mod`: none (client-go already present)
- `package.json`: none

**Complexity:** M

**Risks to check early**
- RBAC: listing pods/deployments cluster-wide needs `list`/`get` on
  `pods` and `deployments` across all namespaces. Fine with a local k3d
  admin kubeconfig; note it explicitly since Phase 10 will need to narrow
  this per-user later.
- Decide the "no namespace selected" default now (all-namespaces vs. a
  fixed default like `default`) — it affects the UI's namespace filter
  design, not just the API.

**Definition of done**
```
kubectl apply -f test-pod.yaml   # any pod manifest, any namespace
```
Refresh Workloads → Pods tab (no live updates yet, per this phase's scope):
the new pod is there, with its real name/namespace/status — not from
`lib/mock/workloads.ts`.

## Phase 2 — Live updates via informers + WebSocket ✅ done

**Goal:** Workloads updates itself when the cluster changes, no refresh.

**Backend**
- Swap `List()` for `k8s.io/client-go/informers` (`SharedInformerFactory`)
  for Pods and Deployments — already part of the `client-go` module already
  required, no new dependency for this half.
- New `internal/stream` package: informer `AddFunc`/`UpdateFunc`/`DeleteFunc`
  handlers convert to typed `{type: added|modified|deleted, resource}`
  events and fan them out to connected clients.
- Streaming transport: **WebSocket**, not SSE — Phase 4 (logs) and Phase 5
  (exec) both need a bidirectional or at least well-understood WS pipeline
  anyway; building one transport pattern now and reusing it in 2/4/5 beats
  maintaining SSE-for-lists and WS-for-exec side by side. New endpoint:
  `GET /api/v1/stream/workloads` (upgrades to WS).
- Frontend WS client feeds diffs into the existing SWR cache via `mutate()`
  with the merged list, rather than replacing SWR's fetch — keeps the "SWR
  is the source of truth for components" model from Phase 0/1 intact.

**Frontend**
- New `useWorkloadsStream` (or extend `useWorkloads`) opening the WS
  connection alongside the existing SWR hook, applying incoming diffs via
  `mutate()`. `WorkloadsPage` itself shouldn't need to change.

**New dependencies**
- `go.mod`: `github.com/gorilla/websocket` (widely used, most examples/docs
  to lean on; `nhooyr.io/websocket` is a more modern alternative if you'd
  rather have a context-first API — either works, gorilla is the safer
  default choice)
- `package.json`: none (native browser `WebSocket`); optionally
  `reconnecting-websocket` for auto-reconnect/backoff instead of hand-rolling it

**Complexity:** L — the biggest jump in the whole plan. Informer lifecycle,
per-connection fan-out, client disconnect handling, and making sure the
informer factory's context is cancelled on the Phase 0 graceful shutdown
path all land here at once.

**Risks to check early**
- Confirm the informer factory actually stops on `SIGINT` locally (leaked
  goroutines are easy to miss until the second `go run .` in a session).
- None from cluster load at k3d scale, but worth a one-line comment in code
  that resync intervals / watch cache size become a real concern only at
  much larger cluster sizes than this dev setup.

**Definition of done**
```
kubectl scale deployment/keycloak --replicas=3 -n auth
```
The Workloads table's Ready column for `keycloak` updates on its own within
1–2 seconds — no manual refresh, no polling interval visible in the network
tab (just the one open WS connection).

## Phase 3 — Pod detail: Overview + Events ✅ done

**Goal:** clicking a real pod shows its real metadata and real events.

> **Outcome note:** `kubectl top pods` worked out of the box on this k3d
> cluster (metrics-server was already installed) — wired the real
> `k8s.io/metrics` client directly instead of shipping the
> always-unavailable stub first. `Handler.MetricsClientset` can still be
> `nil` (no metrics-server) and every usage call degrades to `"—"` rather
> than failing the request, so the graceful-degradation path described below
> is implemented, just not the default on this particular cluster. YAML also
> turned out to be effectively free once the real `corev1.Pod` was already
> in hand (via `sigs.k8s.io/yaml`, already an indirect dependency), so the
> YAML tab is real too, ahead of schedule — Logs/Terminal stay mock-only
> until Phases 4/5.

**Backend**
- `GET /api/v1/pods/{namespace}/{name}` — `clientset.CoreV1().Pods(ns).Get()`,
  mapped to the existing `PodDetail` shape (metadata, labels, containers).
  CPU/Memory usage requires `metrics-server`
  (`k8s.io/metrics` client) — **ship with a hard-coded
  `"metricsAvailable": false"` fallback first**; only wire the real
  `metrics.k8s.io` client once you've confirmed `kubectl top pods` works
  against the target cluster (see risk below). Don't let metrics-server
  availability block the rest of this phase.
- `GET /api/v1/events?involvedObject=<namespace>/<name>` —
  `clientset.CoreV1().Events(ns).List()` with a field selector on
  `involvedObject.name`/`involvedObject.namespace`. Core client-go, no new
  dependency.

**Frontend**
- `getPod(namespace, name)` in `lib/api/workloads.ts` — signature changes
  from name-only (see notes above); `usePod` hook and the dynamic route
  already moved to `[namespace]/[name]` in Phase 1, so this is just filling
  in the real fetch.
- Overview and Events tabs read from the real response; Logs/Terminal/YAML
  tabs stay on mock data until their own phases.

**New dependencies**
- `go.mod`: `k8s.io/metrics` (only once metrics-server is confirmed
  available — see risk below; otherwise defer and ship the
  always-unavailable stub with zero new dependency)
- `package.json`: none

**Complexity:** M

**Risks to check early**
- **Check now, before writing code:** does the target k3d cluster have
  metrics-server installed? Stock k3d does **not** include it by default.
  Run `kubectl top pods` — if it errors, either install metrics-server
  (`kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`,
  with `--kubelet-insecure-tls` for a local cluster) or ship this phase with
  the stub permanently for now and revisit later.

**Definition of done**
Click a real pod row in Workloads → Pod detail's Overview tab shows its
actual namespace/node/pod IP/labels (not `keycloak-6f9d-abc12` from mock
data unless that happens to be the real pod you clicked). Trigger a real
event (e.g. `kubectl delete pod <name>` and let it reschedule, or exceed a
resource limit) and confirm it shows up in the Events tab within a normal
K8s event-propagation delay.

## Phase 4 — Logs ✅ done

**Goal:** the Logs tab is a real live tail, not a static mock.

> **Outcome note:** shipped as a dedicated point-to-point WebSocket
> (`GET /api/v1/pods/{namespace}/{name}/logs`), not multiplexed through
> Phase 2's `Hub` — that pub/sub broadcasts the same event to every
> subscriber, which doesn't fit "one client tailing one container." Real
> per-line timestamps came for free by requesting `PodLogOptions.Timestamps`
> and parsing kubelet's prepended RFC3339 prefix; log *level* has no
> equivalent structure in arbitrary container output, so it's a best-effort
> keyword heuristic (`error`/`warn`/default-info) called out in code as such.

**Backend**
- `GET /api/v1/pods/{namespace}/{name}/logs?container=&follow=true` —
  `clientset.CoreV1().Pods(ns).GetLogs(name, &corev1.PodLogOptions{Follow: true, Container: c}).Stream(ctx)`,
  piped over the **same WebSocket pattern from Phase 2** for infra
  consistency (one streaming code path instead of WS-for-lists,
  SSE-for-logs, WS-again-for-exec in Phase 5).
- `container` param matters now: real pods can have sidecars, unlike every
  pod in the mock data (which has exactly one container) — surface a
  container picker if `pod.containers.length > 1`.

**Frontend**
- Logs tab connects to the WS endpoint via the same hook pattern as
  Phase 2's stream, live-appends lines, autoscrolls unless the user has
  scrolled up manually, and the "Follow" toggle actually opens/closes the
  connection (today it's decorative — see `TerminalPane`'s live-tail label,
  though that specific text lives on the Logs tab in `PodDetailPage`).
- Cap the rendered line buffer (e.g. last 1000 lines) so a chatty container
  doesn't grow the DOM unbounded.

**New dependencies**
- `go.mod`: none (reuses Phase 2's WS library)
- `package.json`: optionally `strip-ansi` if container logs carry ANSI
  color codes you don't want rendered raw — nice-to-have, not required to
  ship this phase

**Complexity:** M

**Risks to check early**
- None cluster-side; the real risk is scope creep into a full log-search/
  filter UI — keep this phase to "live tail + follow toggle + container
  picker," nothing more.

**Definition of done**
```
kubectl logs -f <pod> -n <namespace>
```
running in one terminal and the Logs tab open on the same pod show the same
new lines within a second or two of each other.

## Phase 5 — Terminal (exec) ✅ done

⚠ Shipped unauthenticated, as flagged — accepted deliberately for this
local-only dev cluster rather than gated behind a feature flag. Revisit
before this ever runs anywhere reachable by anyone but the developer, and
close the gap for real in Phase 10.

**Goal:** the Terminal tab is a real shell into the pod, not a scripted demo.

> **Outcome note:** `remotecommand.NewSPDYExecutor` worked against this k3s
> v1.35.5 cluster without any protocol surprises. The WS↔exec bridge needed
> three small adapters (`wsStdin` as `io.Reader`, `wsWriter` as `io.Writer`
> for both stdout/stderr, `wsTerminalSizeQueue` as
> `remotecommand.TerminalSizeQueue`) — not much code, but exactly as fiddly
> as flagged. Verified the distroless/no-shell failure mode explicitly
> (`registry.k8s.io/pause:3.9` has no `/bin/sh`): the session ends with a
> clear in-terminal error instead of hanging.

**Backend**
- New WebSocket endpoint, e.g.
  `GET /api/v1/pods/{namespace}/{name}/exec?container=&command=`, using
  `k8s.io/client-go/tools/remotecommand` (`NewSPDYExecutor`) against the
  pod's `exec` subresource — ships with `client-go`, no new dependency.
  Translate WS frames ↔ the exec `Streams` (stdin/stdout/stderr), plus a
  `remotecommand.TerminalSizeQueue` for resize events coming from the
  frontend.

**Frontend**
- Replace `TerminalPane`'s scripted local-echo (`src/components/ui/TerminalPane.tsx`)
  with a real terminal component backed by `xterm.js`, connected to the exec
  WebSocket. Resize events from `xterm-addon-fit` forward to the backend's
  size queue.

**New dependencies**
- `go.mod`: none (`remotecommand` ships with `client-go`)
- `package.json`: `@xterm/xterm`, `@xterm/addon-fit`

**Complexity:** L — WS framing for stdin/stdout/stderr/resize, PTY
allocation, and `xterm.js` wiring are all genuinely fiddly.

**Risks to check early**
- Containers built from distroless/scratch images have no shell at all —
  design an explicit "no shell available" error state rather than a hung
  connection.
- Confirm the target k3s version's kubelet still serves SPDY exec (the
  WebSocket-based exec subprotocol is the newer alternative in recent K8s
  releases) — check before committing to `remotecommand`'s SPDY executor
  specifically.
- The unauthenticated-exec exposure window called out at the top of this
  file — decide the mitigation (feature flag vs. accept for local-only use)
  before this phase ships, not after.

**Definition of done**
Open the Terminal tab on a real pod, run `ls /` and `whoami` — output
matches `kubectl exec -it <pod> -n <namespace> -- sh -c 'ls / && whoami'`.

## Phase 6 — ConfigMaps & Secrets ✅ done

**Goal:** real ConfigMaps/Secrets, with secret values gated behind an
explicit, audited reveal action — never sent to the frontend by default.

> **Outcome note:** returns the *decoded* plaintext on reveal (not the
> base64 wire form Kubernetes stores it as) — that's what "reveal the
> secret" actually means to a user, matching how other K8s UIs behave.
> Genuinely binary secret values (not text/PEM) would render oddly through
> a JSON string; not handled specially, since real-world secrets people
> want to *read* are virtually always text. Also added a namespace filter
> input to both pages (same pattern as Workloads' Phase 1 filter) — not
> explicitly asked for here, but a real cluster's unfiltered secret/
> configmap list includes every namespace's `kube-root-ca.crt` and Helm's
> internals, which gets noisy fast.

**Backend**
- `GET /api/v1/configmaps?namespace=`, `GET /api/v1/secrets?namespace=` —
  metadata + key names only; secret values are never included here, not
  even masked-but-present (don't send `"••••"` as a stand-in for real
  base64 — send nothing, so there's nothing to accidentally leak client-side).
- `POST /api/v1/secrets/{namespace}/{name}/reveal` — body specifies which
  key(s); decodes and returns the value(s) for **that request only**, and
  writes an audit log line via the Phase 0 `slog` logger on every call
  (who — best-effort as source IP until Phase 10 gives you a real identity;
  when; which secret/key). Response gets `Cache-Control: no-store` so
  neither the browser nor any intermediary caches a decoded secret.

**Frontend**
- `ConfigMapsPage`/`SecretsPage` swap `lib/mock/configmaps.ts` /
  `lib/mock/secrets.ts` for real fetches through `ListDetailSplit`
  (component itself needs no changes).
- Secrets' "Show" button now calls the reveal endpoint (loading state per
  key while in flight) instead of just flipping a local `revealed` boolean
  over an already-present mock value. Keep the decoded value in local
  component state only — don't let it land in the SWR cache, so navigating
  away and back re-masks it and doesn't silently keep the plaintext around.

**New dependencies**
- `go.mod`: none
- `package.json`: none

**Complexity:** M

**Risks to check early**
- Audit log lines must never include the decoded value itself — log the
  key name and requester, never the secret content, or the audit log
  becomes exactly the leak it's meant to catch.
- "Who" in the audit log is genuinely incomplete until Phase 10 — note
  that explicitly in the log line format (e.g. `identity=anonymous(ip=...)`)
  rather than implying more attribution than you actually have.

**Definition of done**
Click "Show" on a real secret key in the UI → the backend's stdout shows an
audit line for that exact reveal, immediately. Open the Network tab in
browser devtools during the initial ConfigMaps/Secrets page load: the
`GET /api/v1/secrets` response contains no decoded values anywhere, only
after the explicit reveal call does the value appear in a response body.

## Phase 7 — Topology graph ✅ done

**Goal:** the topology graph is computed from the real cluster graph, for
any namespace, not hard-coded to one `auth`/`keycloak` shape.

> **Outcome note:** the manual layered-column layout held up fine — never
> needed `dagre`/`elkjs`. Implemented Service→Pod and Deployment→Pod as
> separate edges exactly as specced (not collapsed into a single
> Service→Deployment edge), so a pod targeted by both shows two incoming
> lines; this reads fine visually. ConfigMap/Secret "in use" status is
> computed as a post-pass over collected edges once every Deployment's pod
> template has been scanned. One real limitation surfaced testing against
> `kube-system`: a rank with a dozen-plus nodes (ConfigMaps/Secrets, mostly
> Helm-internal) gets visually cramped — still fully functional (click/
> select all work), just not pretty at that density. Left as-is rather than
> reaching for a layout library over a cosmetic-only issue.

**Backend**
- `GET /api/v1/topology?namespace=X` assembles the graph server-side (the
  frontend should never have to guess relationships):
  - Ingress → Service: match `Ingress.spec.rules[].http.paths[].backend.service.name`.
  - Service → Pods: match `Service.spec.selector` labels against Pod labels.
  - Deployment → Pods: match `Deployment.spec.selector` labels directly
    against Pod labels (skip the ReplicaSet hop for simplicity — the more
    "correct" traversal via owner references matters mainly if multiple
    Deployments have overlapping selectors, which is a rare misconfiguration
    worth a code comment rather than upfront complexity).
  - Deployment → ConfigMap/Secret: scan the pod template's
    `envFrom`/`env[].valueFrom`/`volumes` for `ConfigMapRef`/`SecretRef`
    names.
- No new dependency — this is assembly logic over data you already fetch
  elsewhere, not a new K8s API surface.

**Frontend**
- Replace the hard-coded 7-node fixed-position layout in
  `src/app/(shell)/topology/page.tsx` with a real layout, since node count
  and shape now vary per namespace. Start with a **manual layered-column
  layout** (Ingress column → Service column → Deployment column → Pods
  column, with ConfigMap/Secret hanging off the Deployment column) — the
  graph shapes here are constrained enough that this likely covers it
  without a full graph-layout library. Reach for `dagre` or `elkjs` only if
  that turns out insufficient in practice.
- The Topbar's namespace context (currently the decorative "namespace: auth"
  button on this page) becomes real here, at least for Topology.

**New dependencies**
- `go.mod`: none
- `package.json`: none initially; `dagre` or `elkjs` only if the manual
  layout doesn't hold up

**Complexity:** L — mostly on the backend graph-assembly side; the frontend
layout work is medium once the manual-columns approach is chosen.

**Risks to check early**
- None cluster-side. The real risk is scope creep into a generic graph
  library before confirming the simple layered layout is actually
  insufficient — validate with 2–3 real namespaces of varying shape first.

**Definition of done**

## Phase 10 — Authorization (token-first, with optional Keycloak) + a single image ✅ done

> **Outcome note:** this phase's design changed mid-implementation — an
> earlier version used a Keycloak-only OIDC bearer-token flow with an
> app-level group→namespace/action policy (`internal/authz`,
> `backend/policy.yaml`) and `next-auth` on the frontend. The project owner
> replaced that with what's described below: token-first login, a real
> Kubernetes RBAC pass-through (no app-level policy at all), and OIDC moved
> entirely server-side into the Go backend. That switch also happened to
> eliminate a local environment problem (a Proxifier install on this dev
> machine breaking Node's outbound connections — see AGENTS.md's frontend
> notes) simply by removing the only code path that needed Node to make an
> outbound call at all — the frontend is a static export now, doing
> nothing but `fetch`/WebSocket calls from the browser.
>
> Implemented and verified in full:
> - **Token mode** (`internal/authn`): verified end-to-end with a real,
>   RBAC-scoped ServiceAccount (`list`/`get`/`watch` only, bound to one
>   namespace via a plain `RoleBinding`, not cluster-admin) against
>   `k3d-vinaire-dev`. Login sets the session cookie; a request for that
>   namespace succeeds, a cluster-wide (no-namespace) list or a write
>   action both come back as a real `403` from the Kubernetes API itself
>   (`internal/api.respondK8sError` maps `apierrors.IsForbidden`/
>   `IsUnauthorized`/`IsNotFound` to the right HTTP status — this needed
>   fixing along the way, since every K8s error was originally flattened to
>   `502`). Session TTL syncs exactly to the pasted token's own JWT `exp`
>   claim (verified both with a 1-hour and a 10-minute token). Logout
>   invalidates the session immediately (`401` afterward).
> - **OIDC mode**: a real Authorization Code + PKCE exchange against the
>   dev Keycloak in `/keycloak`, entirely in the Go backend
>   (`internal/authn/oidc.go`) — verified with a real browser login (`curl`
>   for the code-exchange mechanics, then a real Chromium session for the
>   full redirect chain). The resulting session correctly gets a real `401`
>   from the Kubernetes API, since `k3d-vinaire-dev`'s API server isn't
>   itself configured with `--oidc-issuer-url` to trust this realm — that
>   cluster-side RBAC wiring is the "basic scaffold" this phase's spec
>   asked for, not a full production OIDC-to-RBAC setup.
> - **Cross-origin session cookie**: the frontend (a static export, no
>   server of its own) always calls this backend cross-origin, including in
>   local dev. `SameSite=None; Secure=true` is required for a cross-origin
>   `fetch(..., {credentials:"include"})` to carry the cookie at all —
>   confirmed working in a real Chromium browser even over plain
>   `http://localhost` (browsers treat `localhost` as a secure context, so
>   `Secure` doesn't require real TLS there). `COOKIE_SAMESITE=strict` is
>   available for a same-origin deployment instead.
> - **Single combined image**: `docker build .` at the repo root produces
>   one ~50 MB image (multi-stage: `node:22-alpine` builds the frontend,
>   `golang:1.27-alpine` builds the backend, the final layer is
>   `gcr.io/distroless/static-debian12:nonroot` — no shell, no Node/npm, a
>   non-root user by default). `docker run` of that image serves the API
>   and the static frontend from the same port (`STATIC_DIR`, see
>   `backend/static.go`) — verified directly: `/`, `/workloads`, a clean
>   extension-less route, a `/_next/static/...` asset, and
>   `/api/v1/auth/config` all resolved correctly from one running
>   container, and `docker exec ... sh` failed with "no such file" —
>   confirming no shell (let alone Node/npm) exists in the final layer.
> - **Static export routing**: `[namespace]/[name]` dynamic route segments
>   don't work with `output: "export"` (pod/deployment names aren't known
>   at build time), so the two detail pages moved to
>   `/workloads/{pods,deployments}/detail?namespace=&name=` — every `Href`
>   the backend generates (`internal/api.detailHref`) and the one
>   frontend-side link (the deployment detail page's pod-rows table)
>   updated to match. `next dev` still runs as a normal dev server with hot
>   reload — `output: "export"`'s constraints only bind at `next build`.
> - Also removed as part of this rework: `next-auth`, the old
>   `internal/authz` package, `backend/policy.yaml`, and the
>   `frontend/docker-compose.dev.yml` container-workaround this phase
>   briefly needed before OIDC moved server-side — see AGENTS.md's
>   "Authentication (Phase 10)" and "Rendering model" sections for the
>   current design.

**Backend**
- An `AuthProvider` interface with implementations switched via `AUTH_MODE`:
  - `"token"` (default) — login via a pasted Kubernetes ServiceAccount
    token.
  - `"oidc"` — login via Keycloak (or any OIDC provider), available as an
    option once Keycloak is deployed in the cluster.
  - `"disabled"` — for local k3d development, no login at all.
- **Token mode:**
  - `POST /api/v1/auth/login` accepts a pasted K8s token, stores it in a
    server-side session store (an in-memory map to start — swappable for
    Redis later without changing the interface), and generates a random
    session ID.
  - The session ID is handed to the browser as a cookie with
    `HttpOnly` + `Secure` + `SameSite=Strict` — the browser never receives
    or can read the raw K8s token via `document.cookie`.
  - Middleware on every protected route pulls the K8s token out of the
    server-side session by cookie and attaches it to the Kubernetes API
    request's `Authorization` header itself.
  - Session TTL is synced to the K8s token's own TTL (the token is created
    via `kubectl create token --duration=...`) — the session is invalidated
    once it expires, requiring a fresh login.
  - `POST /api/v1/auth/logout` — removes the session from the store and
    clears the cookie.
- **OIDC mode** (active when `AUTH_MODE=oidc`):
  - Authorization Code flow with PKCE via `go-oidc/v3` + `oauth2`.
  - Issuer URL/client ID/secret come from env
    (`OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`), pointing at
    a Keycloak pod in the same cluster (e.g.
    `http://keycloak.auth.svc.cluster.local/realms/vinaire`).
  - After a successful Keycloak login, the same session layer as token
    mode is used — only the identity source differs; the frontend and the
    rest of the backend see no difference.
  - Mapping Keycloak groups to Kubernetes RBAC (`ClusterRoleBinding`) — a
    basic scaffold for now, detailed rules to be refined as it goes.
- `GET /api/v1/auth/config` — tells the frontend which `AUTH_MODE` is
  active, so the UI shows the right login screen.
- README/AGENTS.md gets an example `ClusterRole` manifest with the minimal
  permission set Vinaire needs (**not** cluster-admin), plus the command
  for creating a ServiceAccount + a token with a bounded `--duration`.

**Frontend**
- A login screen: a token-paste field (token mode) + a "Sign in with
  Keycloak" button (shown only when `/api/v1/auth/config` reports `oidc`).
- Every request goes out with `credentials: 'include'` — the cookie rides
  along automatically; no token is ever stored or read from JS.
- A `401` from any protected route → redirect to `/login`.

**Also in this phase: a single backend+frontend image**
- A multi-stage `Dockerfile`: a `node` stage builds the frontend
  (`npm run build`), a `golang` stage builds the backend, and the final
  minimal layer (alpine or distroless, **must** run as a non-root user)
  holds only the Go binary and the frontend's static output next to it.
- In production, the Go backend serves that static output itself
  (`http.FileServer` or `go:embed`) from the same port as the API — one
  process, one pod, one image, the same shape as Headlamp.
- Day-to-day development still runs `npm run dev` and `go run .`
  separately with hot reload — the single image is only built for a
  prod/test deploy into k3d; the local dev loop doesn't change.

**Complexity:** M — the session layer and token login are simple on their
own, but the OIDC branch and folding the build into one Dockerfile add
real volume.

**New dependencies**
- `go.mod`: `github.com/coreos/go-oidc/v3`, `golang.org/x/oauth2` (needed
  for OIDC mode, but added now alongside the interface so it doesn't need
  revisiting later), `github.com/google/uuid` (or equivalent) for
  session-ID generation. Token mode and the combined build need no new
  dependencies.
- `package.json`: none.

**Risks to check early**
- The K8s token itself must never end up in logs — not access logs, not
  error traces; treat it like a password.
- If Keycloak isn't deployed in the cluster yet but `AUTH_MODE=oidc` is set
  anyway, the backend must fail fast at startup with a clear message
  (`"OIDC_ISSUER_URL unreachable"`), not silently break the whole service.
- Folding everything into one image makes it easy to drop basic practices
  (non-root user, a minimal base image) — this is a common mistake when
  moving from separate images to a combined one; check for it explicitly
  in code review.

**Definition of done**
Logging in with a pasted ServiceAccount token works; the browser's DevTools
show the session cookie marked `HttpOnly` and unreachable from the console
via `document.cookie`. Once the token's TTL expires, requests start getting
`401` and the frontend redirects to `/login`. With `AUTH_MODE=oidc` and
Keycloak deployed in the cluster, the "Sign in with Keycloak" button really
logs in through a real realm. `docker build .` at the repo root builds one
image; `docker run` of that image serves both the API and the frontend on
one port, with no node/npm inside the final layer.

## Phase 24 — Cluster management via the web UI ✅ done

**Goal:** connect a second (or third, ...) cluster entirely through
Vinaire's own Settings page — no editing Deployment env vars, no mounting
a kubeconfig Secret by hand, no redeploy. Added not from this roadmap's
original planning but from direct need: the project owner asked "how do I
even connect a second cluster in prod?" after multi-cluster (Phase 11) was
found to only support a static, env-var-configured list.

> ⚠ **This adds a genuinely new write path — the app writing its own
> Secret — flagged and confirmed explicitly with the project owner before
> implementing, per AGENTS.md's core rule.** It's a different *kind* of
> write from Phase 9's three (which act on a user-browsed resource, with
> the caller's own identity): this is Vinaire managing its own
> infrastructure config, with its own in-cluster identity, never exposed
> through any browse/list endpoint. See AGENTS.md's core rule for the
> full description and the narrow, namespace-scoped `Role`/`RoleBinding`
> this needed (create-only on `secrets`, get/update scoped to exactly one
> `resourceName`) — deliberately *not* an addition to the broad, cluster-
> wide read-only `ClusterRole` every browsed cluster's resources go
> through.
>
> **Outcome note:** `internal/clusters.Registry` stopped being "populated
> once at startup, read-only forever" — it now has a mutex (previously
> none at all, safe only because nothing mutated it after boot) plus
> `AddDynamic`/`Remove`, and a lifecycle hook (`SetLifecycleHook`) that
> `main.go` wires to start/stop a cluster's live-update informers. The
> hook exists specifically because `internal/stream` already imports
> `internal/clusters` (for `clientsetFor`/`restConfigFor`) — `clusters`
> importing `stream` back to start informers directly would cycle, so
> `clusters` stays dependency-free and holds only an opaque
> `func(e *Entry) (stop func())` value supplied once from `main.go`, which
> is free to import both. The same fix needed for `stream.ServeWS`'s
> `hubs` map, previously a plain `map[string]*Hub` built once and never
> touched again — now a small mutex-guarded `HubRegistry` type. Persistence
> (`internal/clusters.Store`) is one Secret (`vinaire-clusters`) in this
> backend's own namespace (detected via the standard
> `/var/run/secrets/kubernetes.io/serviceaccount/namespace` file — nothing
> in this codebase read that before), written with a fresh
> `rest.InClusterConfig()` client, deliberately not the possibly-
> `CLUSTER_CONTEXTS`-overridden `Default()` entry — `NewStore` reports
> unavailable (not an error) when the backend isn't running in-cluster at
> all, the same explicit-unavailable pattern as metrics-server/Gateway
> API/Prometheus. `POST /api/v1/clusters` verifies the submitted
> `{name, server, token, caData}` against a real `Discovery().
> ServerVersion()` call *before* persisting anything, so a bad token fails
> loudly immediately. Verified end-to-end against `k3d-vinaire-dev` (in-
> cluster deployment) and a real second cluster, `k3d-vinaire-dev-2`,
> reached from inside the first cluster's pod network via
> `host.docker.internal` (confirmed reachable — DNS resolves through
> CoreDNS's forwarder, TCP connects — with a disposable `busybox` pod

> immediately showed real, distinct data (5 pods/1 namespace vs. the
> default cluster's 7 pods/3 namespaces) in a live Chromium browser after
> switching the Topbar picker, survived a full pod restart
> (`kubectl delete pod`) with zero reconfiguration, and was removed
> cleanly through the same UI (confirm modal → toast), verified gone both
> in the UI and via `GET /api/v1/clusters`.
>
> Also fixed, discovered while building this: `frontend/src/lib/api/http.ts`

> **Outcome note:** Implemented with two deliberate deviations from the

> `POST /api/v1/resources/dry-run`, `POST /api/v1/resources` and
> `PUT /api/v1/resources` take one YAML document and resolve its Kind via
> discovery + the dynamic client, so they work for any kind the cluster
> serves — the project owner chose that over an allowlist, and AGENTS.md's
> write section was rewritten to say so (the caller's own RBAC is still the
> real limit; an ungranted verb is a real 403, verified in-cluster as the
> `vinaire` ServiceAccount). (2) Updates are pinned to a `resourceVersion`
> returned by the dry-run (the diff is computed against exactly that live
> version) instead of trusting the editor's own copy: status churn bumps
> resourceVersion constantly, which made editing a busy Deployment fail with
> a spurious 409 in the first version. Also: strict field validation
> (`FieldValidation: Strict`) is what makes a typo'd field an error — the
> dynamic client otherwise silently drops unknown fields; Secret values are
> redacted from diff responses; dry-run is outside the write rate limiter;
> Monaco is bundled (no CDN) and lazy-loaded; the diff collapses unchanged
> regions. Verified in a real browser against k3d-vinaire-dev: a typo'd
> field gave `unknown field "spec.replicaz"` with the cluster untouched;
> editing a Deployment image through the diff modal changed
> `kubectl get deployment`; "+ Create" created a ConfigMap; the Helm chart
> ClusterRole also gained the Phase 33 scale/pod-delete grants it had missed.

**Goal:** every resource's YAML tab goes from a read-only `<pre>` block to
a real create/edit surface, validated by the cluster itself before
anything is applied.

**Backend**
- `POST /api/v1/{resource}/dry-run` — accepts YAML, runs it through a
  server-side dry-run (client-go, `DryRun: []string{"All"}`) — uses the
  Kubernetes API server itself as the schema/admission-webhook validator,
  no need to bundle or maintain a separate copy of the OpenAPI schema.
- `POST /api/v1/{resource}` (create) and
  `PUT /api/v1/{resource}/{namespace}/{name}` (update) — the real apply,
  only after a successful dry-run.
- Extend the existing YAML tabs (Pod detail, Deployment detail, and every
  other detail page with one) from read-only to edit mode.

**Frontend**
- Replace the static `<pre>` blocks with Monaco Editor
  (`@monaco-editor/react`), YAML syntax highlighting, on every detail page
  that currently shows read-only YAML.
- An "Apply" button — first hits the dry-run endpoint and shows a diff
  (before/after) in a modal; a second click confirms the real apply.
- The existing decorative "+ Create" buttons (Workloads, ConfigMaps,
  Secrets, Network — currently go nowhere) open an empty Monaco Editor
  pre-filled with a template YAML for that resource kind, through the same
  dry-run → apply flow.

**Complexity:** M

**New dependencies**
- `go.mod`: none — dry-run is a standard client-go capability
- `package.json`: `@monaco-editor/react`

**Risks to check early**
- Dry-run validates the schema but doesn't replace a full code review —
  always show the diff before apply, so a change can't accidentally go out
  wider than intended.

**Definition of done**
Editing a Deployment's image via YAML in the UI and clicking Apply —
`kubectl get deployment -o yaml` shows the applied change. A deliberately
invalid YAML (a typo'd field) gives a clear error from dry-run, without
breaking anything in the cluster.

## Phase 26 — Browser-based port-forward ✅ done

> **Outcome note:** Four deliberate deviations from the spec above. (1) Not a
> WebSocket endpoint: the frontend opens `/proxy/…` as a plain browser
> navigation in a new tab, which can't speak WebSocket, so the byte pipe is
> the SPDY port-forward stream used directly as the HTTP transport's
> `net.Conn` (an `httputil.ReverseProxy`; WebSocket upgrades *inside* the
> proxied app go through it too, though that wasn't exercised). No OS port is
> opened — and `k8s.io/client-go/tools/portforward` is used only for its
> protocol constant, since its `PortForwarder` always binds a local listener.
> (2) The URL carries the cluster — `/proxy/{cluster}/{ns}/{pod}/{port}/` —
> because a navigation can't send the `X-Cluster` header and every
> sub-request must stay on the same cluster. (3) `https:8443` in the port
> segment selects TLS (kubectl-proxy's convention). (4) "Forward port" ships
> on Pod detail only: there is no Service detail page to put it on yet.
> **Security:** the proxied page is served from Vinaire's own origin, so a
> hostile pod UI could otherwise act with the user's Vinaire session. It is
> therefore sandboxed (`CSP: sandbox` — verified in a real browser: origin
> `null`, `document.cookie` throws, `fetch('/api/…')` is blocked), the
> session cookie/Authorization are not forwarded, and Set-Cookie is dropped.
> The cost: pod UIs that need cookies/localStorage or use root-relative asset
> paths won't fully work. **Verified against k3d-vinaire-dev:** an nginx pod's
> welcome page opened in a new tab from the button; an HTTPS pod
> (`https:8443`, self-signed) answered; a custom port worked; "nothing
> listening" returns a clear 502 (the kubelet's reason arrives on the error
> stream a millisecond after the data stream's EOF, so reads wait briefly for
> it); and the spec's own risk — forgotten connections — is closed: a
> streaming response aborted by the client or by closing the tab closes its
> pod connection (opened 8 / closed 8, gauge back to 0).

**Goal:** open a port-forward to a pod straight from the browser, the same
convenience `kubectl port-forward` gives on the command line.

**Backend**
- WebSocket endpoint `/api/v1/portforward/{namespace}/pod/{name}?port=N`
  — via client-go (`tools/portforward` + the SPDY dialer) opens a stream
  directly to the pod's port and proxies bytes between that stream and the
  browser's WebSocket connection, without opening a local OS port on the
  server itself.
- Scope for this first iteration is HTTP(S) traffic (a reverse HTTP proxy
  on an authenticated path), not general TCP — covers the large majority
  of real use cases and is significantly simpler to implement.

**Frontend**
- A "Forward port" button on Pod/Service detail — pick a port (from the
  spec's `containerPorts`), opens a new tab at a proxied address like
  `/proxy/{namespace}/{pod}/{port}/`.

**Complexity:** M

**New dependencies**
- `go.mod`: `k8s.io/client-go/tools/portforward`
- `package.json`: none

**Risks to check early**
- The proxy session must close when the tab closes or the WebSocket
  disconnects — otherwise forgotten connections to pods pile up.

**Definition of done**
A pod running any HTTP service inside it — the Forward port button opens
its web UI in a new tab without a single terminal command.

## Phase 28 — Helm application catalog (App Marketplace) ✅ done

> **Outcome note:** Shipped: catalog search and chart pages (README, default
> values), install, upgrade, rollback and uninstall through the Helm SDK
> (`helm.sh/helm/v3` 3.22, which needs the same client-go 0.37 line the project
> already used), a Marketplace section with Catalog and Installed tabs, and a
> Settings help page. Decisions: **(1) Identity** — Helm gets the *caller's own*
> `rest.Config`, never Vinaire's ServiceAccount, so a chart can't do more than the
> user could; the ROADMAP's risk note about "Vinaire's own ServiceAccount needs
> Secret rights" therefore became "the *caller* needs Secret rights in the target
> namespace". **(2) Repositories only from configuration** (`catalog.json` /
> `CATALOG_CONFIG`, https, no credentials): a request can't name a repository or
> URL. The HTTP client refuses loopback/link-local/multicast on the connected
> address, doesn't follow a redirect out of https, caps index/chart sizes, and a
> chart is used only if its download matches the **sha256 in the index** (no
> digest, no install). **(3) Audit** — `helm-install|upgrade|rollback|uninstall`
> plus `-failed` (a failed install can leave objects), never the values;
> reading a release's values (needed to pre-fill an upgrade) is audited as
> `helm-reveal-values`. **(4) Node pinning** works only for charts with a
> top-level `nodeSelector` value; any other layout gets an explicit error rather
> than a guessed path. **(5) The release's source repository** is stored as a
> release label (`vinaire.io/catalog-repo`), since Helm doesn't remember it; for
> releases installed elsewhere the Upgrade dialog asks. **(6) Deviations:** no
> schema-driven form (`react-jsonschema-form` was optional) — the YAML editor sits
> beside the read-only defaults and Helm validates against `values.schema.json` on
> install; the first default list was only six repositories — **widened afterwards
> to about fifty sources by category** (see CHANGELOG), because a catalog without
> PostgreSQL or Kafka is not much of a catalog; **OCI registries are supported**
> (anonymous, TLS-only, size checked from the manifest, content verified by digest,
> read through `oras-go` rather than Helm's registry client, which would use the
> host's Docker credentials) and bring Bitnami's PostgreSQL/MySQL/Redis/Kafka/
> RabbitMQ — Bitnami's old HTTP repository is closed (403 via Broadcom), but its OCI
> charts are alive and point at `bitnami/*:latest` images that exist; `:latest` is
> the only tag Bitnami's free images have, which the catalog says openly. An OCI
> install was verified end to end (Bitnami memcached: pod running, then uninstalled).
> Hashicorp's repository answered 403 from this network (a CloudFront region block)
> and was left out; Artifact Hub as a search source was **deliberately not** added (it
> would let a third party's listing choose what Vinaire installs). **Verified** against the real dev cluster and real repositories:
> pushgateway installed on a chosen node (`helm list` shows it, the pod runs on that
> node, the nodeSelector is on the Deployment); a duplicate name returned 409; a
> chart without a top-level nodeSelector plus a node returned 400; an unknown
> repository 404; upgrade to an older version with new values changed replicas;
> upgrading to a different chart was refused; rollback restored the old state;
> uninstall without the typed name was refused and with it removed everything.
> With a read-only ServiceAccount the cluster answered real 403s for list,
> install and uninstalling Traefik, and Traefik was untouched. The audit lines
> were all present and neither the token nor any values appeared in the log. Not
> exercised live: a chart whose CRDs are missing (the hint is unit-tested), and
> the browser UI itself (type-checked, linted and built, but not clicked through).

**Goal:** install real Helm charts onto the cluster from a browsable
catalog inside Vinaire, without touching a terminal.

**Backend**
- Helm as a Go library (`helm.sh/helm/v3/pkg/action`, `pkg/repo`), **not**
  shelling out to the `helm` binary.
- `GET /api/v1/catalog/charts?search=...` — search across configured Helm
  repositories (the repo list comes from config).
- `GET /api/v1/catalog/charts/{repo}/{chart}` — description, versions, the
  chart's default `values.yaml`, and `values.schema.json` if the chart
  ships one.
- `POST /api/v1/catalog/install` — repo+chart+version, namespace, release
  name, values, including a `nodeSelector` when a specific node is chosen.
- `GET /api/v1/catalog/releases`, `POST .../upgrade`, `POST .../rollback`,
  `DELETE .../uninstall` — all via the Helm SDK.

**Frontend**
- A "Marketplace" section in the sidebar — chart cards, search.
- An install page: a form generated from `values.schema.json` when
  present, otherwise the YAML editor (Phase 25); a namespace picker,
  release name field, and a node dropdown (Phase 19) for `nodeSelector`.
- An "Installed releases" section — Upgrade/Rollback/Uninstall.

**Complexity:** L

**New dependencies**
- `go.mod`: `helm.sh/helm/v3`
- `package.json`: `react-jsonschema-form` (optional — only needed for the
  schema-driven install form)

**Risks to check early**
- Vinaire's own ServiceAccount needs rights on Secrets in the target
  namespace (Helm stores releases as a Secret).
- Some charts require CRDs that Helm doesn't always install ahead of the
  main chart — surface that failure explicitly rather than a generic
  "install failed."
- Keep the repository list configurable, not hardcoded.

**Definition of done**
Pick `postgres` from the catalog via the UI, specify a namespace and a

## Phase 29 — GitOps sync with a choice of backend (ArgoCD or native) ✅ done

> **Outcome note:** Shipped to the spec, with decisions made with the project
> owner before coding (this phase adds write paths): **(1) Identity** — native
> mode runs with nobody logged in, so it applies as a *ServiceAccount token the
> user supplies per source* (checked against the cluster when the source is
> created; a cluster-admin token is flagged), not as Vinaire's own identity. **(2)
> Git** — HTTPS plus an optional read-only token, via `go-git` in memory (no git
> binary, nothing on disk, no argument injection), through a new shared guarded
> HTTP client (`internal/netguard`, which the Helm catalog now uses too); SSH was
> left out. **(3) No pruning** — poll + apply only; removed objects are listed as
> "no longer in git" (kept in memory for the process's life). **(4) Argo CD mode**
> lists Applications, creates one through Phase 25's generic apply (a template, no
> endpoint of its own) and "Sync now" sets the Application's `operation`. Other
> decisions: the mode and the sources are a sealed document next to the cluster
> registry (new `DocStore`; the Secret store now preserves its other keys on save —
> it used to overwrite the whole Secret), and it refuses to store tokens when the
> store isn't encrypted; "in sync" is a server-side dry-run compared with the live
> object — **found by testing**: a dry-run keeps the live resourceVersion, so the
> first version (comparing resourceVersions) called every change "Synced"; `force`
> ("take over fields") is an opt-in per source because without it a field changed by
> kubectl is a conflict, which is what keeps Vinaire from fighting another
> controller. Ordering is Namespaces → CRDs → the rest, with one retry after the
> cluster's API discovery is refreshed (so a custom resource can follow its CRD in one
> sync). **Verified** against the real dev cluster with a real `git http-backend`
> server: a manifest pushed to the repository appeared in the cluster as the limited
> ServiceAccount with no `kubectl apply` (field manager `vinaire-gitops`, labelled with
> its source); a new commit updated it; no-op polls left the resourceVersion alone; a
> Namespace the account may not create came back as the cluster's real 403 on that
> object while the rest synced; a hand edit was reported as a conflict (naming
> `kubectl-patch` and the field) and, with take-over on, reverted within one poll;
> with auto-sync off a poll only reported and Sync now applied; an object removed from
> git was listed as an orphan and **not** deleted; the source and its tokens survived
> a restart; the tokens were not in the backend log, the API responses or the audit
> lines, and the data file was sealed. Argo CD mode was exercised against the
> `applications.argoproj.io` CRD with a stand-in Application (list, detection, the
> native-mode warning, Sync now, a second sync refused as already pending, 404) — **not
> against a real Argo CD controller**, so the sync operation being picked up is
> unverified. Not clicked through in a browser (type-checked, linted, built).

**Goal:** every registered cluster (Phase 11) can have its own GitOps
story — a real ArgoCD it already runs, a minimal built-in poller for
clusters that don't, or nothing at all.

**Backend**
- `GITOPS_MODE` as a setting on each individual registered cluster (not a
  single global env var — different clusters in Phase 11's multi-cluster
  setup may be in different situations): `"argocd"` | `"native"` |
  `"off"`.
- `"argocd"` — extends the existing ArgoCD-detection logic (`isArgoManaged`
  from Phase 9): view/create `Application` resources via the dynamic
  client.
- `"native"` — a minimal in-house poller for clusters without ArgoCD: a
  config of `{repoURL, path, targetRevision, cluster}`, a backend worker
  periodically does a `git pull`, applies manifests via server-side apply
  (Phase 25) to the target cluster, and stores the last-applied commit
  hash plus a Synced/OutOfSync status.
- `"off"` — the GitOps section isn't shown for that cluster at all.

**Frontend**
- A GitOps section in the sidebar (Cluster group) — a list of sync sources
  per cluster, their status, and a "Sync now" button.

**Complexity:** L

**New dependencies**
- `go.mod`: `go-git`, or alternatively an `os/exec` call to the `git`
  binary
- `package.json`: none

**Risks to check early**
- `"native"` mode is essentially a stripped-down ArgoCD of our own — stay
  disciplined about not growing past simple poll+apply (no health checks,
  sync waves, hooks).
- Explicitly warn in the UI if a real ArgoCD is detected on a cluster at
  the same time `"native"` mode is selected for it — that's an apply
  conflict waiting to happen.

**Definition of done**
On a cluster without ArgoCD, configure a native source pointed at a test
git repo, push a manifest there, and wait for sync (or click Sync now) —
the resource appears with no manual `kubectl apply`.

## Phase 30 — Adding worker nodes via SSH ✅ done

> **Outcome note:** Built to the spec, with these decisions. **Token source:**
> the spec says the token is read from the master node, which means SSH access
> to the control plane too (the token isn't in the Kubernetes API) — the form
> supports both pasting the token and a second, optional SSH login to the
> control plane. **Flow:** `POST /nodes/provision/hostkey` (no credentials) →
> the UI shows the fingerprint → `POST /nodes/provision` returns a job id →
> `GET /nodes/provision/{id}/stream` (WebSocket) replays and streams the log.
> The job keeps running if the tab closes (a half-installed node is worse), the
> log is replayable, and the UI falls back to polling if the socket drops.
> Credentials are only in the POST body, never a URL. **Authorization:** the
> caller needs RBAC `create` on `nodes` (a SelfSubjectAccessReview) — SSH
> targets aren't covered by Kubernetes RBAC, so this reuses the cluster's own
> rule for "may this person grow the cluster". **Extra guard rails the spec
> didn't list:** HTTPS-only transport (refused over plain HTTP unless
> `PROVISION_ALLOW_INSECURE`), a target blocklist (loopback, link-local/cloud
> metadata), strict validation + quoting of everything that reaches the remote
> shell, the worker pinned to the control plane's k3s version, and a
> download-to-file installer (a failed `curl | sh` would otherwise exit 0).
> **Verified end to end** against disposable systemd+sshd containers joined to
> k3d-vinaire-dev (real k3s agents, real joins, driven through the real UI):
> a clean server became `Ready` in `kubectl get nodes` with zero commands run
> on it, using (a) root + password with a pasted token and (b) a non-root user
> with password-sudo plus the token read from a control plane over an SSH key;
> a wrong fingerprint aborts with "host key mismatch" before any login. After
> every run the backend log, the job log and the disk were grepped for the
> password, key material and token — nothing. The security-critical parts have
> unit tests (secret formatting never leaks; the validator refuses
> 127.0.0.1/169.254.169.254/injection; a wrong host key sends **zero**
> password attempts to an in-process SSH server). Not covered: a real
> multi-machine network, kubeadm (Phase 35), and removing a node again.

**Goal:** grow a cluster by pointing Vinaire at a bare server's IP and
credentials, instead of running the k3s install script by hand.

**Backend**
- `POST /api/v1/nodes/provision` — host, port (default 22), username,
  auth (password **or** private key — support both, explicitly recommend
  the key in the UI).
- Installation and join are done through a `ClusterProvisioner` interface
  (`Preflight`, `PrepareNode`, `InstallControlPlane`, `JoinWorker`,
  `FetchKubeconfig`). The k3s implementation is described here (via
  `get.k3s.io`); a kubeadm implementation is Phase 35 (joining via
  `kubeadm join`, with the join command obtained on the control-plane
  through `kubeadm token create --print-join-command`).
- The k3s provider's `JoinWorker` uses `golang.org/x/crypto/ssh` to
  remotely run the k3s agent install
  (`curl -sfL https://get.k3s.io | K3S_URL=... K3S_TOKEN=... sh -`); the
  token is pulled from the master node
  (`/var/lib/rancher/k3s/server/node-token`), never hardcoded and never
  logged.
- The install output streams to the client over WebSocket in real time
  (reuses the Phase 5/`TerminalPane` pattern).
- The password/key are used once, for the duration of the request, and
  never persisted to the backend's disk in any form.
- Server host key verification: on first connection, the backend returns
  the fingerprint, the UI shows it to the user for confirmation, and the
  SSH session only continues once confirmed. Use `ssh.FixedHostKey` / a
  custom `HostKeyCallback`, **not** `ssh.InsecureIgnoreHostKey`.

**Frontend**
- An "Add node" button on the Nodes page (Phase 19) — an IP/port/login
  form with a password/SSH-key toggle, and a live install log.

**Complexity:** M

**New dependencies**
- `go.mod`: `golang.org/x/crypto/ssh`
- `package.json`: none

**Risks to check early**
- This is the single most security-sensitive phase in the entire roadmap.
  Credentials must travel only over HTTPS and never end up in access logs
  or error traces, same standard as the Phase 10 Kubernetes token.
- Remotely running a root-level install script with entered credentials is
  a large attack surface if Vinaire itself is ever compromised.
- Unlike Rancher (which just hands you a command to copy and run yourself,
  never touching SSH credentials at all), this approach is more convenient
  but a fundamentally riskier pattern — taken on deliberately, with eyes
  open.

**Definition of done**
Enter a clean server's IP and credentials, click "Add node" — within a
minute or two a new Node shows up in Vinaire's list and in
`kubectl get nodes`, with zero manual commands run on the target server.

## Phase 31 — Create via a form, with a YAML toggle ✅ done

> **Outcome note:** Built as specced, with three deviations. (1) The
> optional ResourceQuota on the Namespace form was left out: it's a second
> object, and Phase 25's apply path is deliberately one document at a time
> (a quota can't even be dry-run before its namespace exists) — it belongs
> with Phase 27's namespace/quota management. (2) `package.json` gained the
> small `yaml` package: reading YAML back into the form needs a real parser.
> (3) The Namespace form is reachable from the Workloads "Create" template
> picker until Phase 27 adds a Namespaces page. "Too complex for the form"
> is detected by a round trip (YAML -> form state -> manifest must equal the
> original), not a field allowlist, so any extra field, sidecar container or
> `valueFrom` env correctly blocks the switch. Verified in a real browser:
> a Deployment created without typing YAML (image, 2 replicas, port, env,
> requests/limits, node) matches the expected `kubectl get`; the generated
> YAML round-trips back into the form; adding `x-extra: 1` blocks the switch
> with the form state intact; ConfigMap, Secret (value stored, input masked)
> and Namespace forms create correctly.

**Goal:** creating the most common resource kinds doesn't require knowing
YAML at all, while staying on the exact same dry-run → apply path Phase 25
already built.

**Backend**
- `GET /api/v1/forms/{resourceType}` — returns a simplified field schema
  for the most common resource kinds (Deployment, ConfigMap, Secret,
  Namespace) — not the full Kubernetes OpenAPI schema (overkill for a
  form), just a small, hand-written set of fields per kind: for
  Deployment — name, namespace, image, replicas, container port, env
  variables (a key/value list), resource requests/limits; for
  ConfigMap/Secret — name, namespace, a key/value list; for Namespace —
  name, optionally a ResourceQuota.
- The form's state is serialized to YAML on the frontend (see below); the
  backend, exactly as in Phase 25, just receives the resulting YAML for
  dry-run/apply — no new backend apply logic needed, the form is only a
  friendlier way to assemble the same YAML.

**Frontend**
- The Create screen gets a "Form / YAML" toggle (a segmented control, the
  same pattern already used on Workloads/Network).
- Form mode: fields driven by `/api/v1/forms/{resourceType}`'s schema —
  for Deployment, reuse the node dropdown from Phase 19 as an optional
  `nodeSelector` (the same logic Phase 28's catalog install form uses).
- Switching Form → YAML serializes the current form state into YAML and
  shows it in Monaco Editor (Phase 25). Switching YAML → Form only works
  if the YAML still matches the simple form's schema — if the resource is
  more complex (custom fields the form doesn't cover), switching back is
  blocked with a clear message ("this YAML is too complex to edit as a
  form"), and the form itself never breaks or loses data on that attempt.
- Past that point, the flow is unchanged: dry-run → diff preview → Apply,
  exactly as Phase 25 already built it.

**Complexity:** M — the form itself is simple, but keeping Form↔YAML in
sync both ways (especially detecting "too complex for the form") needs
careful implementation.

**New dependencies**
- `go.mod`: none
- `package.json`: none beyond the Monaco Editor already added in Phase 25

**Risks to check early**
- The `/api/v1/forms` field schemas are hand-written for these 4 specific
  kinds, not auto-generated from the Kubernetes OpenAPI schema — adding a
  new resource kind's form later means writing its schema by hand again
  each time. A deliberate simplicity-over-completeness tradeoff.

**Definition of done**
Creating a Deployment through the form (without typing a single line of
YAML by hand) — switching to YAML shows a correctly assembled manifest;
the created resource looks identical in `kubectl get` to one applied
through the plain YAML path.

> **Outcome note:** this is a genuinely new extension to AGENTS.md's core

## Phase 34 — Adding a cluster via SSH (create new / connect existing) ✅ done

> **Outcome note:** All four modes shipped: import (SSH), create (SSH), import
> via kubeconfig, and local discovery, plus cluster types, an encrypted
> registry and the Clusters page. Decisions beyond the spec: **(1) Persistence
> outside a cluster.** Phase 24's registry only worked in-cluster (a Secret),
> but local discovery is for a Vinaire running *outside* one, so the registry
> now has two sealed backends — a Secret, or an encrypted file under a new
> `VINAIRE_DATA_DIR` — behind one `Store` interface. **(2) Encryption key**
> comes from `CLUSTER_STORE_KEY`, else a separate Secret / a 0600 key file; an
> in-cluster install whose Role predates the key Secret keeps working but warns
> and stores unencrypted rather than losing its clusters on upgrade (the chart's
> Role now allows the key Secret). **(3) Kubeconfig safety** was the riskiest
> part: a kubeconfig can name a program to run (`exec`) or files to read, so
> only inline data is accepted, plugins/file references/proxy-url are refused,
> and exactly one context is kept — covered by unit tests. **(4)** The same
> cluster under another name is refused by comparing the `kube-system` UID.
> **(5) Gate** for the SSH modes is the caller's RBAC `create` on `nodes`
> (as Phase 30); the kubeconfig/discovery/token adds keep Phase 24's model (no
> extra gate) — worth revisiting in Phase 36's audit. **Verified** against the
> real thing: a clean systemd+sshd server became a working, TLS-verified k3s
> cluster in about a minute with zero commands run on it and registered under a
> certificate address; running create again refused cleanly ("k3s is already
> installed… use Import existing"); import against an address the certificate
> doesn't cover failed with the x509/`--tls-san` explanation and stored
> nothing; removing a registration left the cluster running; local discovery
> found the machine's second k3d cluster, skipped the one already in use and
> added it with its type; an exec-plugin kubeconfig and a file-reference one were
> refused; a duplicate was refused; the on-disk registry contains no plaintext;
> the type override survives a restart; and none of the passwords, keys,
> kubeconfig or token appeared in the backend log. Testing also caught
> relative certificate paths in a local kubeconfig not resolving (fixed), and a
> cluster whose type was detected during a brief outage staying `unknown`
> forever (now retried). Not covered: multi-control-plane HA, kubeadm
> (Phase 35), and a real multi-machine network.

**Goal:** onboard a cluster the same way Phase 30 onboards a node — point
Vinaire at a server's SSH credentials, either to import an existing k3s
install or to turn a clean server into a brand-new one.

The modes below split by *where the cluster lives*. A cluster on **another
server** is reached over SSH or by kubeconfig (the three modes below). A
cluster on **the same machine Vinaire runs on** — the typical home server or
home lab, running k3s (or k3d/kind) rather than a full Kubernetes — is
*discovered locally*, with no SSH at all (the "Local discovery" mode below).
Every registered cluster also gets a detected **type** (k3s, k3d, kind, ...).

**Backend**
- Provisioning is done through the `ClusterProvisioner` interface from
  Phase 30; this phase implements the k3s provider — the kubeadm provider
  is Phase 35. The wizard includes a distribution choice (only k3s is
  available for now).
- Reuses Phase 30's SSH layer (credentials held in memory only for the
  duration of the request, never persisted to disk; the same WebSocket
  log stream; the same mandatory host key verification).
- **Import mode:** `POST /api/v1/clusters/import-ssh` — host, port, user,
  auth (password or key), an optional explicit server URL. The backend
  reads `/etc/rancher/k3s/k3s.yaml` (as root, or via sudo — the sudo
  password comes from what was already entered and is passed over stdin,
  never persisted), substitutes the real address in place of `127.0.0.1`,
  and checks connectivity (`GET /version` against the resulting
  kubeconfig) **before** registering it.
- **Create mode:** `POST /api/v1/clusters/create-ssh` — on a clean server,
  installs k3s server with `--tls-san <public IP or domain>` (required,
  otherwise TLS verification against the external address will fail),
  waits for the API to be ready (`/readyz`), then runs the same steps as
  import mode. A pre-check refuses (with a clear message, without
  overwriting anything) if `/etc/rancher/k3s` already exists on the server
  or port 6443 is already in use.
- A dynamic cluster registry (extends Phase 11's static config): each
  kubeconfig is stored encrypted (AES-GCM, key from an env var or a Secret
  in Vinaire's own namespace) — never in plaintext, never in logs. The
  confirmed host key fingerprint is stored alongside it.
- `DELETE /api/v1/clusters/{name}` — removes only Vinaire's own
  registration, never touches the actual cluster.
- Single-server k3s only for this phase; multi-control-plane HA is out of
  scope.
- **Import-kubeconfig mode:** `POST /api/v1/clusters/import-kubeconfig`
  accepts a kubeconfig (pasted as text or uploaded as a file) with **no**
  SSH involved. Works with any distribution and with managed clusters.
  Checks connectivity (`GET /version`) before saving, same as the SSH
  modes above. The UI shows a recommendation next to it: use a dedicated
  ServiceAccount with only the needed permissions instead of an
  admin-level kubeconfig.
- **Local discovery mode:** for when Vinaire runs directly on a home
  machine or home server (as a binary or a container), *outside* the
  cluster, next to a lightweight distribution such as k3s — and a second
  cluster may exist beside the one it was configured with.
  `GET /api/v1/clusters/discover` is a read-only scan of what the backend
  process can **already see**, nothing more:
  - kubeconfig files: `$KUBECONFIG`, `~/.kube/config`,
    `/etc/rancher/k3s/k3s.yaml`, plus any extra paths from a
    `DISCOVERY_KUBECONFIG_PATHS` env var. Every context that isn't
    registered yet is a candidate. k3d and kind write their own contexts
    (`k3d-<name>`, `kind-<name>`) into the user's kubeconfig, so they are
    found this way — **without ever touching the Docker socket** (mounting
    it into Vinaire is root on the host; deliberately not done).
  - a short, fixed list of well-known local API ports on loopback
    (`6443`, MicroK8s's `16443`, ...) probed for a kube-apiserver — only to
    report "a cluster is listening here but no credentials were found,
    add it via kubeconfig". The probe list is fixed, never user-supplied.
  - each candidate with credentials is probed with a short timeout
    (`GET /version`) for reachability and a type hint.
  - the cluster Vinaire is already using is recognized and left out, by
    comparing the `kube-system` namespace UID (a stable cluster identity),
    not the URL — the same cluster is often reachable as `127.0.0.1`, a LAN
    IP and a hostname at once.
  - read-only and strictly non-escalating: if `/etc/rancher/k3s/k3s.yaml` is
    root-only and Vinaire doesn't run as root, it is reported as "found but
    not readable, here's how to grant access" — Vinaire never invokes
    `sudo` or changes file permissions on its own.
  - unavailable (with an explanatory message, not an empty list) when
    Vinaire runs inside a cluster as a pod — it can't see the host's files.
  Adding a discovered cluster goes through the same path as
  import-kubeconfig: the user confirms *which* candidate (name, server,
  detected type, and whether it carries an admin credential), only **that
  one context's** credentials are extracted and stored encrypted — never the
  whole kubeconfig — and nothing is ever added automatically.
- **Cluster type:** every registry entry carries a `type`:
  `k3s | k3d | kind | minikube | microk8s | kubeadm | managed | unknown`.
  It is detected at registration (all modes, including SSH create, which
  knows it by construction) from cheap, read-only signals: the `+k3s`
  suffix in the server's `gitVersion`, node `providerID` prefixes
  (`k3s://`, `kind://`), node/cluster labels, the `kubeadm-config`
  ConfigMap in `kube-system`, and cloud-provider markers for `managed`.
  Detection is a heuristic, so the user can override it from a dropdown,
  and `unknown` never blocks adding a cluster. The type is persisted with
  the registration (extending Phase 24's `Store`) and exposed on
  `GET /api/v1/clusters`.

**Frontend**
- The cluster picker in the Topbar (Phase 11) gets an "Add cluster" entry
  — a step-by-step wizard: mode (Import existing / Create new / Import via
  kubeconfig) → SSH details (host/port/user + a password/key toggle, or,
  for the kubeconfig mode, a paste-or-upload field instead) → fingerprint
  confirmation (SSH modes only) → a live log (SSH modes only) → success.
  For Create new, an optional final "Add worker nodes" step leads into
  Phase 30.
- A Clusters page (Cluster group in the sidebar): the list of registered
  clusters, their connectivity status, and a Remove button explicitly
  labeled "only removes the connection in Vinaire — the cluster itself is
  untouched."
- A fourth wizard entry, **"Found on this machine"**, shown first when
  discovery is available: a list of discovered candidates with a type
  badge, reachability, and whether it's already added (greyed out), a
  "Rescan" button, and a one-confirmation add. When nothing is readable the
  panel explains exactly what to do (e.g. how to make `k3s.yaml` readable
  to Vinaire's user, or how to mount a kubeconfig read-only into the
  container) instead of showing an empty list.
- The detected **type** appears as a badge in the Topbar cluster picker and
  as a column on the Clusters page, with an edit control to override it.
  The type also tailors the UI: Phase 30's "Add node" is offered only for
  types where adding a machine over SSH makes sense (k3s, and kubeadm once
  Phase 35 lands) and is hidden, with a one-line reason, for k3d/kind
  (their "nodes" are containers), minikube, and managed clusters.

**Complexity:** M — the foundation (SSH, log streaming) already exists
from Phase 30 and Phase 11.
Local discovery plus cluster-type detection add roughly an S on top: no
new dependencies, mostly kubeconfig parsing and read-only probes.

**New dependencies**
- `go.mod`: `golang.org/x/crypto/ssh` (already added in Phase 30);
  `crypto/aes`/`crypto/cipher` from the stdlib for encryption
- `package.json`: none

**Risks to check early**
- TLS SAN: k3s issues its certificate without the public IP by default —
  importing by the external address will fail with an x509 error. Show a
  clear explanation in the UI, plus a "server URL" field to work around
  it.
- SSH might work while port 6443 is unreachable from wherever Vinaire
  itself runs (a VPS firewall, NetBird-style routing) — this is exactly
  why connectivity is checked before anything is saved.
- All connected clusters' admin kubeconfigs living in one place is the
  single most valuable object in the whole system — if Vinaire itself is
  compromised, an attacker gets full access to every connected cluster.
  Consider issuing a dedicated, narrowly-scoped ServiceAccount right after
  import and storing its token instead of the admin certificate (tradeoff:
  a long-lived token).
- Local discovery reads credential files, so it must stay read-only and
  non-escalating, must never log or return a credential (the discover
  response carries names, server URLs, types and "has admin credential:
  yes/no" — never the credential itself), and must only ever extract the
  single context the user chose.
- k3s's `k3s.yaml` is a cluster-admin certificate. Importing it is
  convenient and exactly as powerful as it sounds — show the same
  "use a scoped ServiceAccount instead" recommendation as the kubeconfig
  mode, and offer the narrowly-scoped ServiceAccount flow right after
  adding.
- When Vinaire runs in a container on the home server it can't see the
  host's kubeconfig or loopback ports unless they're deliberately mounted
  or the container uses host networking — discovery will honestly report
  nothing, and the docs must say how to opt in rather than reaching for the
  Docker socket.
- Type detection is a heuristic and will sometimes be wrong (a custom
  distribution, a renamed context). That is why it's editable and why
  nothing hard-depends on it except hiding Phase 30's "Add node".

**Definition of done**
Import: enter a working k3s server's credentials — the cluster appears in
the picker, and switching to it shows its real pods. Create: a clean
server becomes a working cluster in a couple of minutes with zero manual
commands run on it. Running create again against a server that already has
k3s installed refuses cleanly, without breaking anything. Swapping the
host key mid-connection aborts the session.
Local discovery: on a home server running Vinaire next to a k3s cluster
(Vinaire outside the cluster) and a second cluster (a k3d/kind/second k3s
context), "Found on this machine" lists the second one with its detected
type; one confirmation adds it and switching to it shows its real pods; the
cluster Vinaire already uses doesn't show up as a duplicate even if
reachable under several addresses; a `k3s.yaml` Vinaire can't read produces
an actionable message, not an empty list or a silent `sudo`; the type badge
shows in the picker and can be corrected; and the Docker socket is never
touched.

## Phase 35 — A kubeadm provider (full upstream Kubernetes) ✅ done

> **Outcome note:** Shipped behind the same `ClusterProvisioner` interface as
> k3s: preflight, prepare, `kubeadm init` + pinned CNI, worker join, Reset, the
> wizard options, the "what to install next" checklist and Settings help.
> Decisions and deviations: **(1) Pinned versions live in config** —
> `kubeadm.json` (embedded default, or the file named by `KUBEADM_CONFIG`),
> validated at startup: https manifests that carry their pinned tag, exactly one
> default Kubernetes minor and one default CNI. **(2) Cilium is not offered**: it
> installs via `cilium-cli`/Helm, not a plain manifest, so it doesn't fit "apply a
> pinned manifest"; Flannel and Calico are. **(3) Join command hardening** — a
> worker accepts only the exact `kubeadm join host:port --token … --discovery-
> token-ca-cert-hash sha256:…` shape (no control-plane flags) and the command is
> rebuilt from its parsed, single-quoted parts instead of being run as pasted.
> **(4) kubeadm's own output is scrubbed** of the bootstrap token, CA hash and
> certificate key before it reaches the job log — found by testing: kubeadm
> prints them itself. **(5) New-node checks**: hostname and `product_uuid` must
> not collide with an existing node, and the clock must be within 90 s (a skewed
> clock breaks join tokens and certificates). MAC uniqueness is **not** checked —
> the cluster API doesn't expose MACs. **(6) Reset** needs the SSH login again, a
> fresh host-key confirmation and the server's address typed out (re-checked on
> the server), and is audited. **(7)** The wait for a new node to be Ready now
> survives a few transient API errors (permission errors still fail at once) —
> found when one dropped request failed an install that had in fact succeeded.
> Out of scope as planned: RHEL-family OSes, multi-control-plane HA.
> **Verified** on a real Ubuntu 22.04 systemd server (disposable container): a
> clean machine became a working Kubernetes v1.37 cluster with Flannel and CoreDNS,
> registered as type `kubeadm` with its pods visible in Vinaire; the bootstrap
> token and CA hash were masked in the log; a worker joined via the join command
> read off the control plane and registered; Reset returned the machine to clean
> (a wrong confirmation address was refused with a 400), and a fresh create after
> it succeeded. **Test-environment caveats, not product bugs:** inside a nested
> container kube-proxy can't write `nf_conntrack_max` (read-only `/proc/sys`) and
> the control plane eventually became unstable on a 4 GB WSL VM, so the CoreDNS
> wait needed `conntrack.maxPerCore: 0` applied by hand; on a real machine or VM
> this doesn't arise. Not exercised end-to-end: the Ready-wait fix itself after
> a successful join, and Calico.

**Goal:** the same create/join experience as Phase 30/34, but for a real
upstream Kubernetes install via kubeadm, not just k3s.

**Backend**
- A `ClusterProvisioner` implementation for kubeadm. Debian/Ubuntu only —
  OS detection via `/etc/os-release`, refusing with a clear message on
  anything unsupported (an RHEL-family implementation is separate, later
  work). Uses the same SSH layer, log streaming, and host key verification
  as Phase 30/34.
  - **Preflight:** root/sudo access; at least 2 CPUs and 2 GB RAM; swap
    status; the required ports are free (6443, 2379-2380, 10250-10259);
    `pkgs.k8s.io` and `registry.k8s.io` are reachable; hostname/MAC/
    `product_uuid` are unique among the cluster's existing nodes.
  - **PrepareNode:** `swapoff` plus removing swap from `fstab`; the
    `overlay` and `br_netfilter` kernel modules (made persistent via
    `/etc/modules-load.d`); `sysctl`
    `net.bridge.bridge-nf-call-iptables=1` and `net.ipv4.ip_forward=1`
    (via `/etc/sysctl.d`); installing containerd with
    `SystemdCgroup=true`; adding the `pkgs.k8s.io` repository for the
    chosen minor version; installing `kubelet`/`kubeadm`/`kubectl`; and
    pinning those packages (`apt-mark hold`).
  - **InstallControlPlane:** `kubeadm init` with `--pod-network-cidr`
    matching the chosen CNI, `--apiserver-cert-extra-sans <public IP or
    domain>`, and optional `--control-plane-endpoint`/
    `--kubernetes-version`; installs the chosen CNI (Flannel by default,
    or Calico, or Cilium) from manifests at **pinned versions in the
    backend's own config**, never "latest"; waits for the node to be
    Ready and for CoreDNS to be Running.
  - A "single-node" option: removes the
    `node-role.kubernetes.io/control-plane` taint, so workloads can be
    scheduled on the control-plane node too.
  - **FetchKubeconfig:** reads `/etc/kubernetes/admin.conf`, then
    registers the cluster the same way Phase 34 does.
  - **JoinWorker:** `kubeadm token create --print-join-command` on the
    control-plane, then runs that join command on the worker after its
    own Preflight+PrepareNode.
  - **Reset:** a `kubeadm reset -f` action, clearing CNI config and
    iptables rules, for a node whose install failed partway through or
    that's being removed from the cluster — gated behind double
    confirmation.
  - The list of supported Kubernetes minor versions lives in the backend's
    own config, not hardcoded — defaulting to the latest stable at release
    time.

**Frontend**
- In Phase 34's wizard, a "Kubernetes (kubeadm)" distribution option,
  version and CNI dropdowns, a "single-node" checkbox, and an optional
  control-plane endpoint field (a VIP or DNS name) with the hint "set this
  now if you're planning HA — adding it later is hard." A final checklist
  of "what to install next" (an Ingress controller, a StorageClass,
  metrics-server), linking to the Marketplace (Phase 28).

**Complexity:** L — the heaviest provisioning phase in terms of step count
and OS-specific detail.

**New dependencies**
- `go.mod`: none
- `package.json`: none

**Risks to check early**
- The pod CIDR must match what the chosen CNI expects, or pods won't get
  networking — and the failure doesn't show up immediately.
- Not setting a control-plane endpoint at `init` time makes turning the
  cluster into an HA one later practically impossible.
- A partially-failed install leaves the node in an undefined state, which
  is exactly why Reset is mandatory.
- A kubeadm cluster has no Ingress, StorageClass, or metrics-server out of
  the box — without them, Phase 3 (metrics) and Phase 32 (charts) will
  show "unavailable" until they're installed.
- Clock drift between nodes breaks join and certificates — add an NTP/
  chrony check to Preflight.

**Definition of done**
A clean Ubuntu server becomes a working cluster through the wizard with
zero manual commands — `kubectl get nodes` shows Ready. Adding a worker
through Phase 30 with kubeadm selected ends with a Ready node. A
deliberately interrupted install recovers via Reset and can be retried
from scratch.

**Goal:** verify specific security properties across the whole project
(Phases 1–35) and lock them in with automated CI checks. This is not a
guarantee of "no vulnerabilities" — it's a set of checkable claims. The
audit's outcome is written up in `docs/security.md` (a short threat model
+ the list of verified properties + known residual risks).

**Backend**
1. **Authorization on informer-cache reads.** Informers run under the
   backend's own ServiceAccount, so cached data is **not** naturally
   scoped to a calling user's RBAC. Before serving anything out of the
   cache, check the caller's own permissions via `SelfSubjectAccessReview`
   (using their own token — verb, resource, namespace), caching that
   result briefly (seconds). A resource the caller can't `list`/`get`
   must never be served or surfaced — including in search (Phase 20),
   topology (Phase 7), or the Dashboard. This applies per cluster in the
   registry (Phase 11, 34) independently.
2. **Secrets:** never hold decoded Secret values in the informer cache
   (metadata only, or the `data` field stripped) — a value is only ever
   returned through the explicit reveal endpoint (Phase 6), audit-logged,
   and permission-checked.
3. **Cluster registry (Phase 34):** kubeconfigs are stored encrypted only
   (AES-GCM, key from an env var or a Secret — never from the repo or the
   image); the decrypted value lives in memory only for the duration of a
   request; a kubeconfig never appears in the API or in logs, including
   error responses; the encryption key can be rotated without losing the
   registry (re-encrypt in place).
4. **SSH provisioning (Phase 30, 34, 35):** host key verification is
   mandatory everywhere (`FixedHostKey`, never
   `InsecureIgnoreHostKey` — enforced via a codebase grep and a linter
   rule); passwords, keys, and sudo passwords are never written to disk
   and never end up in logs, error traces, or the log stream sent to the
   client; commands run on the remote server are built from fixed
   templates, with user input (host, username, versions, CIDR, endpoint)
   validated against strict formats and never interpolated into a shell
   string unescaped; Kubernetes/CNI versions only ever come from the
   backend's own config list; join tokens and k3s tokens are never logged.
5. **Logs:** a middleware that strips the `Authorization` header,
   `Cookie`/`Set-Cookie`, Kubernetes tokens, Secret values, SSH
   credentials, kubeconfigs, and request bodies on login/reveal/
   provision/import from every log line. A canary-value test: a token, an
   SSH password, and a recognizably-tagged kubeconfig fragment, run
   through the main flows, then confirm the tag appears in no log output
   at all.
6. **Sessions:** `HttpOnly` + `Secure` + `SameSite=Strict`, random session
   IDs of sufficient length (`crypto/rand`), full invalidation on logout
   and at TTL expiry, a fresh session ID issued after login (session
   fixation protection), and a login-attempt rate limit (per IP and per
   account, with backoff).
7. **CSRF and WebSocket:** check `Origin`/`Sec-Fetch-Site` on every
   mutating request and on every WebSocket endpoint's handshake (logs,
   exec, port-forward, the event stream, the provisioning log stream) as
   defense in depth on top of `SameSite`.
8. **Headers and CORS:** `Content-Security-Policy` (no `unsafe-inline`
   where avoidable), HSTS, `X-Content-Type-Options: nosniff`,
   `frame-ancestors 'none'`, `Referrer-Policy`. CORS only via an explicit
   origin allowlist — never `*` together with credentials.
9. **SSRF and path traversal:** the port-forward proxy (Phase 26) only
   ever reaches pods through the Kubernetes API, never an arbitrary
   user-supplied host/URL; the Helm repository list (Phase 28) is
   validated (HTTPS only, internal addresses blocked unless explicitly
   allowed); a cluster-import server URL (Phase 34) is validated the same
   way; path checks everywhere a path is built from user input (Phase
   29's git paths, chart extraction).
10. **Dangerous actions:** exec (Phase 5), YAML apply (Phase 25), Helm
    install (Phase 28), SSH provisioning (Phase 30, 34, 35), adding/
    removing clusters (Phase 34), Scale/Delete (Phase 9, 33) — for each
    one, confirm the request either runs under the caller's own token or
    goes through an explicit permission check (actions on Vinaire itself,
    like adding a cluster or SSH provisioning, need their own role/
    permission, not available to ordinary users), and that the action
    lands in the audit log (who, when, what, result).
11. **Vinaire's own permissions:** verify its ServiceAccount's RBAC with
    `kubectl auth can-i --list --as=system:serviceaccount:<ns>:<name>` —
    no wildcard rules (`"*"`), no cluster-admin; rights on Secrets only
    where actually needed (Helm, Phase 28).
12. **Dependencies and repo secrets:** `govulncheck`, `gosec` for Go;
    `npm audit` for the frontend; `gitleaks` across the full git history;
    Dependabot.

**Frontend**
1. Data coming from the cluster is untrusted input (pod names,
   annotations, labels, event messages, log lines, provisioning output).
   Forbid `dangerouslySetInnerHTML` for this data (an ESLint rule), render
   it as text only; for ANSI-colored logs, use a safe parser that never
   inserts HTML.
2. Tokens, kubeconfigs, and SSH credentials are never stored in

3. Secret values shown via "Show" are cleared from state when leaving the

**Infrastructure**
1. The image (Phase 10): non-root, `readOnlyRootFilesystem`, drop `ALL`
   capabilities, `seccompProfile: RuntimeDefault`,
   `allowPrivilegeEscalation: false`, explicit requests/limits — reflected
   as defaults in the Helm chart (Phase 21).
2. A `NetworkPolicy` in the chart: inbound only from the Ingress
   controller; outbound only to the Kubernetes API (including external
   clusters in the registry), provisioning servers' SSH port, DNS, and the
   configured Prometheus/Loki/Alertmanager/Helm repositories.
3. A deployment recommendation in the README: don't expose Vinaire
   directly to the internet — access it over a VPN/NetBird; if it must be
   exposed, only behind HTTPS with cert-manager-issued TLS. Separately
   flag that Vinaire, once it holds a cluster registry, is a single point
   with access to every connected cluster.
4. A "security" CI job (extending `ci.yml` from Phase 0/23):
   `govulncheck`, `gosec`, `npm audit`, `gitleaks`, and `trivy` against the
   built image (failing on fixable HIGH/CRITICAL findings). Runs on a

## Phase 39 — Все ресурсы (универсальный просмотр) ✅ done

**Источник:** `docs/gap-analysis.md`, пункт A (P1). Сравнение с Headlamp и Rancher показало главный
разрыв: у Vinaire нет страниц для CronJob, ReplicaSet, HPA, PodDisruptionBudget, NetworkPolicy,
ServiceAccount, Endpoints и **Events**, и нет аналога «More Resources» — доступа к любому виду из
API discovery.

**Сделано.** Страница **All resources** (`/resources`): слева виды, которые отдаёт discovery *этому
пользователю* (91 в dev-кластере), с поиском по имени, kind, short names и группе; сверху ярлыки
на Events, CronJobs, ReplicaSets, HPA, PDB, NetworkPolicies, ServiceAccounts, Endpoints (только те,
что есть в кластере). Справа — таблица вида с **теми же колонками, что печатает `kubectl get`**:
бэкенд просит у API-сервера Table-представление (`Accept: …as=Table`), поэтому у каждого вида
свои осмысленные колонки (включая CRD), без ручных страниц. Фильтр по namespace и по строкам,
колонка Namespace при просмотре по всем, лимит 500 строк с пометкой «обрезано». Объект открывается
на `/resources/detail` с вкладками Overview и YAML; правка YAML идёт через уже существующий
generic apply (Phase 25: dry-run → diff → apply) — новых записей эта фаза **не добавляет**.

**Бэкенд:** `GET /api/v1/api-resources`, `…/{group}/{version}/{resource}/objects[?namespace=]`,
`…/objects/{name}` (`internal/api/allresources.go`). Всё читается **от имени вызывающего**; перед
запросом group/version/resource/namespace/name проверяются строгими шаблонами, вид сверяется с
discovery (неизвестный — 404), путь собирается только из проверенных частей. Ошибка 403 несёт
настоящую фразу API-сервера (`cronjobs.batch is forbidden: …`).

**Secrets.** В списке — только то, что показывает kubectl (имя, тип, число ключей, возраст); у
отдельного Secret значения в YAML заменены на `<redacted>`, вкладка YAML только для чтения, а
apply **отвергает** манифест Secret с такими заглушками — иначе сохранение затёрло бы настоящие
значения. Расшифровка — по-прежнему только через аудируемый `reveal`.

**Не вошло.** Метки-фильтры и сортировка по колонкам (это фаза «Таблицы», следующая по плану);

**Сделано.** На странице ноды — панель действий: **Cordon / Uncordon**, **Drain**, **Edit labels**,

- **Delete node** — удаляет только объект Node (машина и kubelet не трогаются — работающий kubelet
  зарегистрирует ноду снова); нужно ввести имя.
- **Chart:** отдельная неприкреплённая роль `<fullname>-node-admin` (nodes get/list/watch/patch/delete,

**Сделано.** На странице Access control: кнопка **Bind a role** (вкладки RoleBindings и

ClusterRoleBinding — только на ClusterRole; удаление — ввести имя привязки; имена, субъекты и
namespace проверяются строгими шаблонами; созданные привязки получают метку
`app.kubernetes.io/managed-by: vinaire` и аннотацию `vinaire.io/created-by`. Аудит: `rbac-bind`,
`rbac-bind-failed`, `rbac-unbind`. Длинный отказ Kubernetes (десятки строк прав) превращается в одну
понятную фразу.

**Chart:** отдельная неприкреплённая роль `<fullname>-rbac-admin` (create/delete привязок, чтение
ролей, `subjectaccessreviews`, и `bind` **только** на роли самого чарта — viewer, installer,
node-admin, rbac-admin, admin): администратор может раздавать роли Vinaire, не будучи
cluster-admin.

`cluster-admin` и `edit` без права — **403 от самого Kubernetes** («attempting to grant RBAC
permissions not currently held»), cluster-wide без подтверждения — 400, ответ «может ли»
(разрешено в своём namespace, нет — в чужом), привязки субъекта с правилами, защита `cluster-admin`,
аудит. Плюс прогон в браузере (привязка, отказ при эскалации, подтверждение, удаление, «Can they…?»).

**Не вошло.** Создание и правка Role/ClusterRole (сознательно); привязка ко всем группам сразу;

**Loki находится сам и читается через API-сервер.** Бэкенд ищет Service Loki по меткам и обращается к нему

**Не вошло.** Распределённый Loki и объектное хранилище (S3); Grafana и дашборды; алерты по логам;

## Phase 46 — Единый язык интерфейса (переключатель RU/EN) ✅ done

**Источник:** `docs/gap-analysis.md`, пункт H (P2): интерфейс был смесью английского и русского.

**Сделано.** В верхней панели — переключатель **RU / EN**. Язык по умолчанию — язык браузера
(русский браузер получает русский), выбор запоминается в cookie `vinaire_lang` (не в web storage — оно
запрещено линтером; в cookie лежит только `en` или `ru`). Английский текст в коде остаётся «ключом»:
разработчик по-прежнему пишет обычный английский, а словарь `src/lib/i18n/dict/ru.json` (824 записи)
даёт русский. Справка в Settings написана по-русски, для английского режима у неё есть
`dict/en.json` (372 записи). Строка, которой нет в словаре (имя пода, сообщение сервера), проходит как есть.

**Как устроено.** Переводится не DOM, а сами React-элементы при создании: `tsconfig.json` задаёт
`jsxImportSource` на `src/lib/i18n/runtime`, чья обёртка `jsx/jsxs/jsxDEV` прогоняет текстовые
дети и атрибуты `placeholder`/`title`/`aria-label`/`alt` **хост-элементов** через `tr()` (точное
совпадение, пробелы по краям сохраняются). Так переведены и константы уровня модуля (вкладки,
заголовки колонок), а React остаётся хозяином страницы — без MutationObserver. Для слов, которые
надо переставлять, есть `t("{n} of {m}", {n, m})`. Смена языка пересоздаёт поддерево по ключу
(`I18nProvider`). Статический HTML всегда английский, первый клиентский рендер совпадает с ним
(`getServerLang()`), сохранённый язык применяется сразу после гидратации — ошибок гидратации нет.

**Проверка.** `npm run check:i18n` (в CI, job фронтенда): падает, если в коде появился русский
фрагмент без записи в `en.json` или в словарях есть пустое значение; английские строки без перевода
только перечисляются (много текста приходит с сервера). Проверено в браузере: RU — боковое меню, вход,
страницы; EN — вся справка Settings без кириллицы; клик по переключателю меняет язык на лету.

**Не вошло.** Блоки кода с русскими комментариями в справке остаются как есть (перевод склеил бы
строки); сообщения об ошибках бэкенда не переводятся; другие языки — добавить словарь и значение `Lang`.

**Сделано.** Settings → **Sign-in**: мастер берёт у администратора Keycloak URL, логин и пароль, и
через Admin REST API (`internal/keycloak`) создаёт — идемпотентно — **realm**, **confidential-клиента**
для Vinaire (только authorization code + PKCE; без password grant и service account; redirect URI и web
origin — ровно адрес Vinaire, без подстановок; существующий *public*-клиент отвергается) и, по желанию,
первого пользователя. После этого OIDC discovery проверяет, что realm и секрет рабочие, и вход через
Keycloak **включается на лету** (`authn.Manager.ConfigureOIDC`), а при перезапуске восстанавливается
(`RestoreOIDC`, с повторами, пока Keycloak не ответит). Экран входа показывает кнопку «Sign in with
Keycloak» и, пока не отключено, форму токена; выключатель «разрешить вход по токену» нельзя перевести в
положение «выключено», пока OIDC не включён — так нельзя запереть всех. «Turn Keycloak sign-in off»
забывает только сторону Vinaire (Keycloak не трогается).

**Безопасность (см. AGENTS.md).** Пароль администратора — в теле POST, только по защищённому
соединению, в `keycloak.Secret`, один запрос токена, нигде не хранится, не логируется и не возвращается.
Хранится только секрет нового клиента — запечатанным в хранилище реестра кластеров (`auth-oidc`);
**незашифрованное хранилище отказывает**. URL Keycloak приходит из запроса, поэтому все обращения (мастер,
discovery, обмен кода, ключи) идут через `netguard` (https, без loopback/link-local;
`OIDC_ALLOW_INSECURE=true` — только для разработки). Все ручки закрыты `requireVinaireRight` на
виртуальном ресурсе `auth.vinaire.io` (роль `-admin` чарта), аудит `keycloak-setup` / `-failed` /
`keycloak-token-login` / `keycloak-disable` без учётных данных. Недоступно при `AUTH_MODE=disabled` и
`AUTH_MODE=oidc` (там настройка у оператора).

**Что мастер сделать не может.** Сделать так, чтобы **API-сервер кластера доверял** этому издателю
(`--oidc-issuer-url` и др.) — это настройка самого кластера. Мастер показывает готовые флаги и пример
привязки роли; без них вход проходит, а обращения к кластеру получают 401.

**Проверено вживую** на Keycloak из `keycloak/docker-compose.yml`: настройка из UI, перенаправление на
Keycloak и возврат с сессией, восстановление после перезапуска, переключатель токена, отключение; в
логах нет паролей и секретов. Тесты: `internal/keycloak`, `internal/authn/runtime_oidc_test.go`,
`internal/api/keycloak_test.go`, тест «закрытых» ручек.

**Не вошло.** Ротация секрета клиента, привязка групп Keycloak к ролям Kubernetes, настройка API-сервера
из Vinaire (для k3s — отдельная фаза, см. Phase 51), другие OIDC-провайдеры мастером (работают через
`AUTH_MODE=oidc`).

## Phase 48 — Сессии вне памяти и несколько реплик (безопасность) ✅ done

**Риск из `docs/security.md`:** сессии живут в памяти одного процесса — перезапуск разлогинивает всех,
больше одной реплики запускать нельзя, а в сессии лежит настоящий токен Kubernetes до 12 ч.

**План.**
- `authn.Store` уже интерфейс: добавить реализацию в запечатанном общем хранилище — Secret/ConfigMap
  кластера (через `vinaire-clusters-key`) либо Redis/etcd-совместимое, выбор — отдельное решение. Токен
  Kubernetes в хранилище — **только запечатанным** (AES-GCM тем же ключом), id сессии — хэш (SHA-256), а не
  открытое значение, чтобы дамп хранилища не давал входа.
- Лимитер входа и ограничитель записей — общие между репликами (счётчики в том же хранилище).
- Живые подписки (informers/WebSocket) остаются на реплику; проверить, что они не зависят от «липкости».
- Чарт: `replicaCount > 1` разрешается, только если выбрано общее хранилище сессий; `PodDisruptionBudget`.
- Сокращение срока: «скользящий» таймаут простоя (idle) и отзыв сессии администратором (список активных
  сессий в Audit/Settings).

**Сделано.** Выбрано хранилище **Secret `vinaire-sessions` в собственном namespace Vinaire** (без новой
инфраструктуры; решение принято по умолчанию как самое узкое по правам — отдельный Redis можно добавить позже
за тем же интерфейсом `authn.Store`). `SESSION_STORE=secret` (чарт: `sessions.store: auto|memory|secret`,
`auto` = secret при `replicaCount > 1`): каждая сессия — **один ключ** Secret, меняется merge-патчем только
этого ключа (две реплики не затирают друг друга), значение **запечатано** тем же ключом, что реестр кластеров;
имя ключа — SHA-256 от id сессии, а не сам id (дамп Secret не даёт cookie). Без ключа шифрования режим отказывается
запускаться (токен Kubernetes открытым не хранится). Реплика держит снимок общего состояния (обновляется раз в
3 с; неизвестный cookie вызывает одну внеочередную проверку не чаще раза в 0,5 с), отзыв и выход доходят до
других реплик за секунды; при недоступном хранилище действует последний снимок, а **новый вход честно
отказывает**. Предел — 200 сессий (Secret ≤ 1 МиБ). Janitor убирает просроченные и нечитаемые записи.
**Список сеансов** (Settings → Sign-in): кто вошёл и до когда, «Завершить сеанс» (`GET /api/v1/auth/sessions`,
`DELETE .../{ref}`, право `auth.vinaire.io`, аудит `session-revoke`; ref — короткий отпечаток, не cookie и не
токен). **Лидер**: при нескольких репликах планируемые опросы GitOps выполняет только реплика, державшая Lease
`vinaire-leader` (`LEADER_ELECTION=true`, ставится чартом); «Sync now» выполняется там, где нажат. Чарт: при
`replicaCount > 1` — `sessionAffinity: ClientIP` у Service (запущенная установка/провижининг живёт на своей
реплике), `PodDisruptionBudget`, Role получила `get/patch` на `vinaire-sessions` и права на Lease; значения вроде
`replicaCount: 2` + `sessions.store: memory` отвергаются при установке.

**Проверено вживую** (две реплики в k3d): вход на реплике A принимается репликой B; Secret не содержит токена в
открытом виде; убийство реплики A и перезапуск обеих не разлогинивают; отзыв на одной реплике действует на
другой; ровно одна реплика — лидер. Тесты: `authn/shared_test.go` (две реплики, срок, предел, отказ
хранилища, список/отзыв), `clusters/sessions_kv_test.go`, `leader/leader_test.go`, `api/sessions_test.go`.

**Осталось на реплике (не общим):** ограничитель попыток входа (эффективный предел — N× на N реплик), реестр
фоновых установок Helm и запусков провижининга (поэтому affinity), живые подписки (informers). Скользящий
таймаут простоя не сделан — срок сессии по-прежнему ограничен 12 ч.

**Complexity:** M–L. **Зависимости:** Phase 36 (аудит), Phase 47.

## Phase 49 — Изоляция учётных данных кластеров (безопасность) ✅ done

**Риск:** один реестр хранит учётные данные всех подключённых кластеров под одним ключом; компрометация
Vinaire или `CLUSTER_STORE_KEY` раскрывает все.

**План.**
- Ключ из внешнего источника: KMS/Vault/облачный KMS (envelope encryption: ключ данных на каждый кластер,
  главный ключ — снаружи), `CLUSTER_STORE_KEY` остаётся как простой режим.
- Учётные данные **на кластер** запечатаны отдельным ключом; расшифровка — только в момент использования, в
  памяти не держатся дольше запроса (кроме информеров).
- Короткоживущие токены вместо бессрочных: подключение через ServiceAccount с `TokenRequest` (срок
  ~1 ч, автообновление) вместо вставленного вечного токена, где кластер это позволяет.
- Раздельные права: кто может добавлять кластер (`clusters.vinaire.io`) и кто может читать его учётные
  данные (никто — только Vinaire); аудит каждого использования учётных данных фоновой задачей.
- Ротация и отзыв: «перевыпустить токен кластера» одной кнопкой; предупреждение о токенах без срока.

**Решение владельца проекта:** «если у людей есть KMS/Vault — ключ там, если нет — ключ в Secret».

**Сделано.**
- **Ключ вне кластера.** `KEY_PROVIDER=vault` (чарт: `keyProvider.type: vault`; работает с HashiCorp Vault и
  OpenBao — Transit engine). Ключ данных хранилища (32 байта, которым запечатаны реестр кластеров, GitOps,
  вход через Keycloak и общие сеансы) хранится **только обёрнутым** ключом Transit; в Secret `vinaire-clusters-key`
  (или в файле `store.key.wrapped` на домашнем сервере) лежит `vault:v1:…`, а сырого ключа нет нигде, кроме памяти
  Vinaire. Тот, кто прочитал все Secret'ы namespace, получает бесполезный блоб: нужен доступ к Vault со своим
  контролем и журналом аудита. Вход — токен (`VAULT_TOKEN`/файл) или **Kubernetes auth** сервис-аккаунтом пода;
  токен Vault кэшируется до истечения аренды. Адрес и параметры — только из конфигурации оператора, `http://` — лишь
  с `VAULT_ALLOW_INSECURE=true` (разработка). Без провайдера всё работает как раньше (`CLUSTER_STORE_KEY` или
  управляемый Secret); `CLUSTER_STORE_KEY` вместе с провайдером отвергается как неоднозначность.
- **Миграция без перешифровки.** Существующее хранилище с сырым ключом при первом старте с провайдером получает **тот
  же** ключ, обёрнутый Vault'ом, а сырая копия удаляется; данные читаются без изменений.
- **Отказ вместо подмены.** Недоступный Vault при старте — повторы, затем выход (никакого «нового ключа» и
  незашифрованного хранилища); хранилище, обёрнутое провайдером, не открывается без `KEY_PROVIDER` или с другим
  провайдером (`ErrKeyUnavailable`, выход).
- **Ротация ключа в Vault.** Повернули ключ Transit → один раз `KEY_REWRAP_ON_START=true` (чарт
  `keyProvider.rewrapOnStart`): обёрнутый ключ переезжает на новую версию (`rewrap`), сам ключ через Vinaire не
  проходит.
- **Состояние учётных данных кластеров.** У добавленных кластеров с токеном в списке видно: «токен бессрочный»,
  «скоро истечёт» (< 7 дней), «истёк» (по `exp` токена; сам токен не показывается). **«Заменить токен»**
  (`PUT /api/v1/clusters/{name}/credentials`, право `clusters.vinaire.io`, только по защищённому соединению):
  новый токен проверяется живым вызовом, должен принадлежать **тому же кластеру** (UID namespace `kube-system`),
  затем заменяет старый в реестре и в работающем процессе; аудит `rotate-cluster-credentials` без токена. Кластеры из
  kubeconfig (там может быть сертификат) так не меняются — импортируйте kubeconfig заново.

**Проверено вживую** с настоящим Vault 1.18 (dev, Transit): запуск без провайдера → с провайдером (сырой
`store.key` исчез, появился `store.key.wrapped` с `vault:v1:`), кластер на месте после перезапуска; замена токена
кластера (плохой токен отвергнут); поворот ключа Transit и `rewrap` до `vault:v2:`; Vault остановлен — Vinaire не
стартует; хранилище без `KEY_PROVIDER` не открывается; в `clusters.enc` и в логах нет токенов.

**Рассмотрено и не сделано — и почему.**
- *Отдельный ключ на каждый кластер* (HKDF от общего ключа или привязка шифртекста к имени кластера через AAD): не
  даёт защиты, которой нет сейчас, — кто владеет общим ключом, получает и производные, а кто им не владеет, подменить
  запечатанный блоб не может. Настоящая развязка — отдельные ключи Transit на кластер с вызовом Vault при каждом
  использовании; это добавило бы Vault в горячий путь и приносит мало, пока учётные данные всё равно живут в памяти
  процесса. Если понадобится — отдельная фаза.
- *Автоматические короткоживущие токены (TokenRequest)*: для этого у Vinaire должно быть право выпускать токены для
  сервис-аккаунта целевого кластера — то есть ещё одна, более широкая запись. Вместо этого сделаны предупреждения и
  простая замена токена (выпустить `kubectl create token … --duration=…` и вставить).
- *Облачные KMS (AWS/GCP/Azure) напрямую*: интерфейс `keyprovider.Provider` готов, но без тестового аккаунта
  реализация была бы непроверенной; для облаков Vault/OpenBao в роли посредника работает уже сейчас. Добавляется как
  отдельный провайдер.
- *Журнал каждого использования учётных данных*: у кластера в аудите самого Kubernetes и так видны действия под
  токеном; у ключа — аудит Vault.

**Complexity:** L. **Зависимости:** Phase 24, 34, 36.

- **Правило «тело запроса ограничено»** (`TestEveryRequestBodyIsSizeLimited`) нашло **пять обработчиков без

- **Фаззинг** (11 целей, `go test -fuzz`): разбор kubeconfig (инвариант: принятое — одна context, без exec/auth-provider/

- *NetworkPolicy включённой по умолчанию*: политика уже есть (`networkPolicy.enabled`), но правила зависят от CNI и

- *`automountServiceAccountToken: false`*: Vinaire использует токен пода для информеров, Secret реестра и Lease —
  отключить нельзя.
- *Внешний пентест и ревью* — **за владельцем проекта**: пакет готов; результаты вносить в `docs/security.md`.
- *Нагрузочные проверки* чтения, числа WebSocket и веера информеров — не делались (указано в пакете как непокрытое).

**Complexity:** M (подготовка) + внешний этап. **Зависимости:** Phase 36, 48, 49.

## Phase 51 — Обновление версии кластера (P3) ⏳ planned

закреплённого в бэкенде списка; control-plane, затем агенты по одному с `cordon`/`drain` из Phase 40 и
проверкой Ready между шагами) и **kubeadm** (`kubeadm upgrade plan/apply`, затем `upgrade node`, затем
kubelet). Предпроверки: разрыв версий не больше одной минорной, PodDisruptionBudget, свободные ресурсы,
резервная копия etcd/снимок (k3s `etcd-snapshot`), пользовательские API (deprecated APIs: проверка
манифестов на удалённые версии API). Учётные данные SSH — по правилам Phase 30 (в памяти, пин ключа хоста,
HTTPS). Возможность отката только для k3s с снимком. Для managed-кластеров — только показ версии и ссылка
на обновление у провайдера.

**Решение до начала (AGENTS.md):** новые записи (обновление ноды по SSH, drain) — отдельное обсуждение.
**Complexity:** L. **Зависимости:** Phase 30, 34, 35, 40.

## Phase 52 — Облачные провайдеры (EKS, GKE, AKS) (P3) 💤 отложена (решение владельца, 2026-10-08)

> Отложена «в долгий ящик»: не планируется, пока владелец проекта не вернётся к ней. Описание сохранено.

**Идея.** Подключать managed-кластеры, учётные данные которых получаются через плагин провайдера
(`exec`/`auth-provider`), который Vinaire сейчас осознанно отвергает.

**План.** Не запускать произвольные команды на сервере Vinaire. Вместо этого — нативные SDK по узкому
списку: AWS (`eks:GetToken` через STS presign, IRSA/роль на под), GCP (workload identity, `container.clusters.get`),
Azure (AAD token через workload identity). Импорт кластера по облачному аккаунту с перечислением
кластеров; токены — короткоживущие, обновляются автоматически; учётные данные облака — через роль/identity
пода, а не вставленный ключ; если ключ неизбежен — запечатанным по Phase 49. Тип кластера «managed»
получает собственные возможности (список нод-групп, версия, ссылка в консоль провайдера), без управления
через SSH.

**Решение до начала:** это новая поверхность доверия (облачные права); граница прав и модель идентичности
согласуются отдельно. **Complexity:** L. **Зависимости:** Phase 34, 49.

## Phase 53 — Проекты (P3) ⏳ planned

**Идея.** Группировка namespace в «проекты» (как в Rancher) с общими квотами, членами и фильтром по
проекту в интерфейсе.

**План.** Проект = метка `vinaire.io/project=<имя>` на namespace + ConfigMap/CRD-подобная запись в
собственной конфигурации Vinaire? — по принципу AGENTS.md права решает Kubernetes, поэтому: проект
хранится **в самих namespace** (метка и аннотации), а не в закрытой базе Vinaire; «члены» — это обычные
RoleBinding'и, создаваемые через Phase 44; квоты — ResourceQuota/LimitRange через Phase 25. Интерфейс:
переключатель проекта в верхней панели (фильтр всех списков), страница проекта (namespace, квоты, использование,
участники), создание namespace «в проекте» с квотой по шаблону.

**Решение до начала:** метка на чужие namespace — запись в кластер (через общий apply), формулировка права
на создание проекта. **Complexity:** M. **Зависимости:** Phase 25, 27, 41, 44.

## Phase 54 — Сканы CIS (P3) ⏳ planned

**Идея.** Проверка кластера по CIS Kubernetes Benchmark и показ результатов.

**План.** Запуск `kube-bench` как Job от имени пользователя (закреплённый образ, закреплённая версия,

SelfSubjectAccessReview). Результаты — страница «Security scans»: проверки по разделам, статус
PASS/WARN/FAIL, текст исправления, история запусков (в ConfigMap namespace запуска или в собственном
хранилище), экспорт. Для managed-кластеров — профиль провайдера (eks/gke/aks). Дополнительно: быстрые
проверки Vinaire без Job (RBAC с `*`, Secret без шифрования в etcd — по признакам, Pod Security, открытые
NodePort, образы `latest`).

**Решение до начала:** создание привилегированного Job — новая запись и повышенный риск. **Complexity:** M.
**Зависимости:** Phase 25, 28.

## Phase 55 — Плагины (P3) ⏳ planned

**Идея.** Расширения интерфейса и бэкенда без форка проекта — но без права выполнять произвольный JS в
оригине Vinaire (CSP, Phase 36).

**План.** Модель «плагин = отдельный контейнер/сервис + манифест». Манифест (YAML) объявляет страницы
(встраиваемые в `iframe` с `sandbox` и отдельным origin), пункты меню и **запрашиваемые права**; бэкенд
проксирует запросы плагина **от имени пользователя** по уже существующим API (никаких собственных
учётных данных у плагина), через ограниченный набор ручек и с лимитами. Установка плагина — Helm-путь из
Phase 28 из каталога оператора (подписанные чарты), включение — через `requireVinaireRight`. Без
загрузки кода плагина в страницу Vinaire; общение с хост-страницей — только `postMessage` по
узкому протоколу (тема, язык, выбранный кластер/namespace).

**Решение до начала:** граница доверия и список возможностей. **Complexity:** L. **Зависимости:** Phase 28, 36,
48.
