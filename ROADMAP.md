# Roadmap

Vinaire ships in **vertical slices**, not horizontal layers. Every phase below
is one end-to-end feature — a real backend endpoint wired to the real frontend
screen that already exists (built against mock data) — not "all the backend"
followed by "all the frontend." Each phase ends with something you can click
through in a browser against a local k3d cluster, and a concrete **Definition
of done** you can run yourself to confirm it actually works before moving on.

Phases are ordered read-only → live → interactive → write → secured →
multi-cluster on purpose. The order is fixed; scope inside a phase can flex.

Current state this plan builds on: `/frontend` is a fully built UI on mock
data (Next.js + TypeScript + Tailwind, SWR-based data layer with a clean
`lib/api/*` seam already in place for swapping mocks for real fetches), and
`/backend` is a Go + chi + client-go skeleton with one working endpoint
(`GET /healthz`) and a read-only Kubernetes client stub.

## Notes on the current repo (read before starting Phase 0)

A few things surfaced while re-reading `/frontend`, `/backend`, and
`AGENTS.md` against this plan. None of them require changing README.md or
AGENTS.md right now — they're either already consistent, or gaps to close
*as part of* the phase where they start to matter. Flagging them here so
they don't get lost.

- **CORS target port is `3100`, not `3000`.** The frontend was moved off
  Next.js's default port earlier (port 3000 is taken by another local tool
  on this machine) — `frontend/package.json`'s `dev`/`start` scripts already
  run on `-p 3100`, and README.md already documents this. Phase 0's CORS
  config below uses `3100` accordingly.
- **Pod/Deployment detail routes are name-only — this will break on real
  data.** `src/app/(shell)/workloads/pods/[name]/page.tsx` and the
  `deployments/[name]` equivalent, plus `getPod(name)` / `getDeployment(name)`
  in `lib/api/workloads.ts`, key purely by resource name. That's fine for
  mock data (names happen to be globally unique), but two different
  namespaces can absolutely have a pod named the same thing on a real
  cluster. **Fix this at the Phase 1 boundary**, before real data starts
  flowing: routes become `/workloads/pods/[namespace]/[name]` (same for
  deployments), and the `WorkloadRow.href` values generated by the backend
  already encode the right path. Doing it in Phase 1 means Phase 3 doesn't
  have to re-touch routing.
- **`internal/k8s` staying read-only holds through Phase 8, by design.**
  Re-checked every phase against AGENTS.md's core rule ("no write verbs in
  `internal/k8s`, no direct K8s writes from the UI"). Phases 0–8 never add a
  write verb. Phase 9 is specifically the GitOps-PR flow AGENTS.md already
  describes — its write actions live in a **new** `internal/gitops` package,
  never in `internal/k8s`, and never call `Create`/`Update`/`Patch`/`Delete`
  against the cluster. No doc changes needed; Phase 9 is AGENTS.md's rule
  being implemented, not bent.
- **`AGENTS.md`'s repository-structure tree will go stale incrementally**,
  not all at once — phases 1–11 each add a backend package
  (`internal/api`, `internal/stream`, `internal/gitops`, `internal/auth`,
  `internal/cluster`, ...) that doesn't exist yet. Recommend updating that
  tree phase-by-phase, in the same PR as the phase that introduces the new
  package, rather than speculatively now.
- **README.md's Prerequisites section doesn't yet say how to stand up the
  local k3d cluster** Phase 1's Definition of done assumes exists (it only
  says "a reachable cluster... k3d is the intended dev target"). Worth
  adding a concrete `k3d cluster create vinaire-dev` snippet — good scope
  for the Phase 1 PR, since that's the first phase that actually needs one
  running.
- **Data-fetching library: already decided.** `frontend` already uses
  [SWR](https://swr.vercel.app/), installed and wired through
  `lib/hooks/*.ts`. Keeping it rather than introducing React Query — SWR's
  API is a better fit for this app's shape (mostly key-based GETs, no
  complex mutation/cache-invalidation graphs), it's smaller, and it's from
  the same team as Next.js. Phase 0 below documents this as a confirmed
  decision, not an open question.
- **⚠ Security-sequencing flag on Phase 5.** Terminal/exec lets you run
  arbitrary commands inside a real pod. As sequenced, Phase 5 ships *before*
  Phase 10 (auth). Between those two phases, anyone who can reach the dev
  server has an unauthenticated shell into any pod in the cluster. This
  doesn't change the phase order (you asked not to), but it's worth an
  explicit decision before Phase 5 ships: either gate Terminal behind a
  `TERMINAL_ENABLED=false`-by-default env flag until Phase 10 lands, or
  accept the exposure for a local-only dev cluster. Flagging it now so it's
  a conscious choice, not a surprise during a later security pass.

## Phase 0 — Dev infrastructure ✅ done

**Goal:** both apps boot cleanly, talk to each other, and prove it in the UI.

**Backend**
- New `internal/config` package: load `PORT` (default `8080`), `KUBECONFIG`
  (already read ad hoc in `internal/k8s/client.go` — centralize it here),
  and `CORS_ALLOWED_ORIGINS` (default `http://localhost:3100`) from env with
  sane defaults, so nothing *requires* env vars to run locally.
- Replace `log` with `log/slog` (stdlib since Go 1.21 — **zero new
  dependency**) for structured logging; log every request's method/path/
  status/duration and the CORS origin on startup.
- CORS middleware restricted to the configured origin(s) — needed the
  moment the frontend makes a real cross-origin fetch in Phase 1.
- Graceful shutdown: `http.Server` combined with `signal.NotifyContext`
  (`SIGINT`, `SIGTERM`) and `Shutdown(ctx)`. Doesn't matter much yet, but
  Phase 2's informers need clean teardown and it's cheaper to build the
  habit now than retrofit it.

**Frontend**
- `lib/api/config.ts` already exports `API_BASE` from
  `NEXT_PUBLIC_API_BASE` — add a small `apiFetch<T>(path): Promise<T>`
  wrapper next to it (JSON parsing, non-2xx → thrown `ApiError`) that every
  real `lib/api/*.ts` function will call starting Phase 1. No behavior
  change yet — the mock functions keep returning mock data.
- Add a minimal connection-status indicator (a small dot + label is enough
  — reuse the `StatusDot` component) somewhere in the shell, e.g. next to
  the alerts bell in `Topbar`, backed by a new `useHealthz()` SWR hook
  polling `GET /healthz` every few seconds.

**New dependencies**
- `go.mod`: `github.com/go-chi/cors`
- `package.json`: none (SWR already installed)

**Complexity:** S

**Risks to check early**
- None operationally — this phase is plumbing. The one thing worth
  double-checking: the CORS origin literally has to match `http://localhost:3100`
  exactly (scheme + host + port), or the browser silently blocks the
  Phase 1 fetch with an opaque CORS error that's annoying to debug blind.

**Definition of done**
```
npm run dev   # from repo root — starts backend :8080 and frontend :3100
```
Open the frontend: the status indicator shows "backend: connected" once
`/healthz` resolves. Stop the backend process (Ctrl+C on it alone, or kill
`:8080`): within one poll interval the indicator flips to "unreachable" and
the rest of the UI keeps working (no crash, no white screen).

## Phase 1 — Pods & Deployments (read-only, `List()`, no live updates) ✅ done

**Goal:** Workloads' Deployments and Pods tabs show your real cluster.

**Backend**
- `internal/k8s`: `ListPods(ctx, namespace string) ([]corev1.Pod, error)` and
  `ListDeployments(ctx, namespace string) ([]appsv1.Deployment, error)` via
  `clientset.CoreV1().Pods(ns).List()` / `clientset.AppsV1().Deployments(ns).List()`.
  Empty `namespace` = all namespaces (`""` in the K8s API already means
  cluster-wide list).
- New `internal/api` package (handlers), wired up in `main.go`:
  `GET /api/v1/pods?namespace=`, `GET /api/v1/deployments?namespace=`.
  Response shape matches the frontend's existing `WorkloadRow` type exactly
  (`name`, `namespace`, `ready`, `status`, `statusColor`, `restarts`, `age`,
  `href`) — the mapping/status-derivation logic (pod phase → color,
  ready-replicas-vs-desired → Healthy/Degraded) is the actual business logic
  in this phase, not the HTTP plumbing around it.
- **Do the same for StatefulSets/DaemonSets/Jobs in this phase too** — not
  in the original phase text, but it's the identical `List()` + map pattern
  with zero extra design cost once Pods/Deployments are done, and it avoids
  the Workloads page having 2 real tabs and 3 permanently-mock tabs.
- **Apply the namespace-in-route fix from the notes above**: `href` values
  the backend generates for each row are `/workloads/pods/{namespace}/{name}`
  and `/workloads/deployments/{namespace}/{name}`.

**Frontend**
- Update the pod/deployment detail routes to
  `[namespace]/[name]` (currently `[name]` only).
- `lib/api/workloads.ts`: `getWorkloads(kind)` calls
  `apiFetch(`/api/v1/${kind}?namespace=${ns}`)` instead of returning
  `workloadsMock[kind]`. `lib/hooks/useWorkloads.ts` and every component
  consuming it (`WorkloadsPage`, `DataTable`) need **zero changes** — this
  is exactly the seam the mock-data layer was built for.
- Namespace filter: reuse the existing (currently decorative) namespace
  affordance, or add a simple `<select>` for now — full namespace-context
  plumbing isn't needed until Phase 7.

**New dependencies**
- `go.mod`: none (client-go already present)
- `package.json`: none

**Complexity:** M

**Risks to check early**
- RBAC: listing pods/deployments cluster-wide needs `list`/`get` on
  `pods` and `deployments` across all namespaces. Fine with a local k3d
  admin kubeconfig; note it explicitly since Phase 10 will need to narrow
  this per-user later.
- Decide the "no namespace selected" default now (all-namespaces vs. a
  fixed default like `default`) — it affects the UI's namespace filter
  design, not just the API.

**Definition of done**
```
kubectl apply -f test-pod.yaml   # any pod manifest, any namespace
```
Refresh Workloads → Pods tab (no live updates yet, per this phase's scope):
the new pod is there, with its real name/namespace/status — not from
`lib/mock/workloads.ts`.

## Phase 2 — Live updates via informers + WebSocket ✅ done

**Goal:** Workloads updates itself when the cluster changes, no refresh.

**Backend**
- Swap `List()` for `k8s.io/client-go/informers` (`SharedInformerFactory`)
  for Pods and Deployments — already part of the `client-go` module already
  required, no new dependency for this half.
- New `internal/stream` package: informer `AddFunc`/`UpdateFunc`/`DeleteFunc`
  handlers convert to typed `{type: added|modified|deleted, resource}`
  events and fan them out to connected clients.
- Streaming transport: **WebSocket**, not SSE — Phase 4 (logs) and Phase 5
  (exec) both need a bidirectional or at least well-understood WS pipeline
  anyway; building one transport pattern now and reusing it in 2/4/5 beats
  maintaining SSE-for-lists and WS-for-exec side by side. New endpoint:
  `GET /api/v1/stream/workloads` (upgrades to WS).
- Frontend WS client feeds diffs into the existing SWR cache via `mutate()`
  with the merged list, rather than replacing SWR's fetch — keeps the "SWR
  is the source of truth for components" model from Phase 0/1 intact.

**Frontend**
- New `useWorkloadsStream` (or extend `useWorkloads`) opening the WS
  connection alongside the existing SWR hook, applying incoming diffs via
  `mutate()`. `WorkloadsPage` itself shouldn't need to change.

**New dependencies**
- `go.mod`: `github.com/gorilla/websocket` (widely used, most examples/docs
  to lean on; `nhooyr.io/websocket` is a more modern alternative if you'd
  rather have a context-first API — either works, gorilla is the safer
  default choice)
- `package.json`: none (native browser `WebSocket`); optionally
  `reconnecting-websocket` for auto-reconnect/backoff instead of hand-rolling it

**Complexity:** L — the biggest jump in the whole plan. Informer lifecycle,
per-connection fan-out, client disconnect handling, and making sure the
informer factory's context is cancelled on the Phase 0 graceful shutdown
path all land here at once.

**Risks to check early**
- Confirm the informer factory actually stops on `SIGINT` locally (leaked
  goroutines are easy to miss until the second `go run .` in a session).
- None from cluster load at k3d scale, but worth a one-line comment in code
  that resync intervals / watch cache size become a real concern only at
  much larger cluster sizes than this dev setup.

**Definition of done**
```
kubectl scale deployment/keycloak --replicas=3 -n auth
```
The Workloads table's Ready column for `keycloak` updates on its own within
1–2 seconds — no manual refresh, no polling interval visible in the network
tab (just the one open WS connection).

## Phase 3 — Pod detail: Overview + Events ✅ done

**Goal:** clicking a real pod shows its real metadata and real events.

> **Outcome note:** `kubectl top pods` worked out of the box on this k3d
> cluster (metrics-server was already installed) — wired the real
> `k8s.io/metrics` client directly instead of shipping the
> always-unavailable stub first. `Handler.MetricsClientset` can still be
> `nil` (no metrics-server) and every usage call degrades to `"—"` rather
> than failing the request, so the graceful-degradation path described below
> is implemented, just not the default on this particular cluster. YAML also
> turned out to be effectively free once the real `corev1.Pod` was already
> in hand (via `sigs.k8s.io/yaml`, already an indirect dependency), so the
> YAML tab is real too, ahead of schedule — Logs/Terminal stay mock-only
> until Phases 4/5.

**Backend**
- `GET /api/v1/pods/{namespace}/{name}` — `clientset.CoreV1().Pods(ns).Get()`,
  mapped to the existing `PodDetail` shape (metadata, labels, containers).
  CPU/Memory usage requires `metrics-server`
  (`k8s.io/metrics` client) — **ship with a hard-coded
  `"metricsAvailable": false"` fallback first**; only wire the real
  `metrics.k8s.io` client once you've confirmed `kubectl top pods` works
  against the target cluster (see risk below). Don't let metrics-server
  availability block the rest of this phase.
- `GET /api/v1/events?involvedObject=<namespace>/<name>` —
  `clientset.CoreV1().Events(ns).List()` with a field selector on
  `involvedObject.name`/`involvedObject.namespace`. Core client-go, no new
  dependency.

**Frontend**
- `getPod(namespace, name)` in `lib/api/workloads.ts` — signature changes
  from name-only (see notes above); `usePod` hook and the dynamic route
  already moved to `[namespace]/[name]` in Phase 1, so this is just filling
  in the real fetch.
- Overview and Events tabs read from the real response; Logs/Terminal/YAML
  tabs stay on mock data until their own phases.

**New dependencies**
- `go.mod`: `k8s.io/metrics` (only once metrics-server is confirmed
  available — see risk below; otherwise defer and ship the
  always-unavailable stub with zero new dependency)
- `package.json`: none

**Complexity:** M

**Risks to check early**
- **Check now, before writing code:** does the target k3d cluster have
  metrics-server installed? Stock k3d does **not** include it by default.
  Run `kubectl top pods` — if it errors, either install metrics-server
  (`kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`,
  with `--kubelet-insecure-tls` for a local cluster) or ship this phase with
  the stub permanently for now and revisit later.

**Definition of done**
Click a real pod row in Workloads → Pod detail's Overview tab shows its
actual namespace/node/pod IP/labels (not `keycloak-6f9d-abc12` from mock
data unless that happens to be the real pod you clicked). Trigger a real
event (e.g. `kubectl delete pod <name>` and let it reschedule, or exceed a
resource limit) and confirm it shows up in the Events tab within a normal
K8s event-propagation delay.

## Phase 4 — Logs

**Goal:** the Logs tab is a real live tail, not a static mock.

**Backend**
- `GET /api/v1/pods/{namespace}/{name}/logs?container=&follow=true` —
  `clientset.CoreV1().Pods(ns).GetLogs(name, &corev1.PodLogOptions{Follow: true, Container: c}).Stream(ctx)`,
  piped over the **same WebSocket pattern from Phase 2** for infra
  consistency (one streaming code path instead of WS-for-lists,
  SSE-for-logs, WS-again-for-exec in Phase 5).
- `container` param matters now: real pods can have sidecars, unlike every
  pod in the mock data (which has exactly one container) — surface a
  container picker if `pod.containers.length > 1`.

**Frontend**
- Logs tab connects to the WS endpoint via the same hook pattern as
  Phase 2's stream, live-appends lines, autoscrolls unless the user has
  scrolled up manually, and the "Follow" toggle actually opens/closes the
  connection (today it's decorative — see `TerminalPane`'s live-tail label,
  though that specific text lives on the Logs tab in `PodDetailPage`).
- Cap the rendered line buffer (e.g. last 1000 lines) so a chatty container
  doesn't grow the DOM unbounded.

**New dependencies**
- `go.mod`: none (reuses Phase 2's WS library)
- `package.json`: optionally `strip-ansi` if container logs carry ANSI
  color codes you don't want rendered raw — nice-to-have, not required to
  ship this phase

**Complexity:** M

**Risks to check early**
- None cluster-side; the real risk is scope creep into a full log-search/
  filter UI — keep this phase to "live tail + follow toggle + container
  picker," nothing more.

**Definition of done**
```
kubectl logs -f <pod> -n <namespace>
```
running in one terminal and the Logs tab open on the same pod show the same
new lines within a second or two of each other.

## Phase 5 — Terminal (exec)

⚠ See the security-sequencing note at the top of this document before
shipping this phase — it's unauthenticated until Phase 10.

**Goal:** the Terminal tab is a real shell into the pod, not a scripted demo.

**Backend**
- New WebSocket endpoint, e.g.
  `GET /api/v1/pods/{namespace}/{name}/exec?container=&command=`, using
  `k8s.io/client-go/tools/remotecommand` (`NewSPDYExecutor`) against the
  pod's `exec` subresource — ships with `client-go`, no new dependency.
  Translate WS frames ↔ the exec `Streams` (stdin/stdout/stderr), plus a
  `remotecommand.TerminalSizeQueue` for resize events coming from the
  frontend.

**Frontend**
- Replace `TerminalPane`'s scripted local-echo (`src/components/ui/TerminalPane.tsx`)
  with a real terminal component backed by `xterm.js`, connected to the exec
  WebSocket. Resize events from `xterm-addon-fit` forward to the backend's
  size queue.

**New dependencies**
- `go.mod`: none (`remotecommand` ships with `client-go`)
- `package.json`: `@xterm/xterm`, `@xterm/addon-fit`

**Complexity:** L — WS framing for stdin/stdout/stderr/resize, PTY
allocation, and `xterm.js` wiring are all genuinely fiddly.

**Risks to check early**
- Containers built from distroless/scratch images have no shell at all —
  design an explicit "no shell available" error state rather than a hung
  connection.
- Confirm the target k3s version's kubelet still serves SPDY exec (the
  WebSocket-based exec subprotocol is the newer alternative in recent K8s
  releases) — check before committing to `remotecommand`'s SPDY executor
  specifically.
- The unauthenticated-exec exposure window called out at the top of this
  file — decide the mitigation (feature flag vs. accept for local-only use)
  before this phase ships, not after.

**Definition of done**
Open the Terminal tab on a real pod, run `ls /` and `whoami` — output
matches `kubectl exec -it <pod> -n <namespace> -- sh -c 'ls / && whoami'`.

## Phase 6 — ConfigMaps & Secrets

**Goal:** real ConfigMaps/Secrets, with secret values gated behind an
explicit, audited reveal action — never sent to the frontend by default.

**Backend**
- `GET /api/v1/configmaps?namespace=`, `GET /api/v1/secrets?namespace=` —
  metadata + key names only; secret values are never included here, not
  even masked-but-present (don't send `"••••"` as a stand-in for real
  base64 — send nothing, so there's nothing to accidentally leak client-side).
- `POST /api/v1/secrets/{namespace}/{name}/reveal` — body specifies which
  key(s); decodes and returns the value(s) for **that request only**, and
  writes an audit log line via the Phase 0 `slog` logger on every call
  (who — best-effort as source IP until Phase 10 gives you a real identity;
  when; which secret/key). Response gets `Cache-Control: no-store` so
  neither the browser nor any intermediary caches a decoded secret.

**Frontend**
- `ConfigMapsPage`/`SecretsPage` swap `lib/mock/configmaps.ts` /
  `lib/mock/secrets.ts` for real fetches through `ListDetailSplit`
  (component itself needs no changes).
- Secrets' "Show" button now calls the reveal endpoint (loading state per
  key while in flight) instead of just flipping a local `revealed` boolean
  over an already-present mock value. Keep the decoded value in local
  component state only — don't let it land in the SWR cache, so navigating
  away and back re-masks it and doesn't silently keep the plaintext around.

**New dependencies**
- `go.mod`: none
- `package.json`: none

**Complexity:** M

**Risks to check early**
- Audit log lines must never include the decoded value itself — log the
  key name and requester, never the secret content, or the audit log
  becomes exactly the leak it's meant to catch.
- "Who" in the audit log is genuinely incomplete until Phase 10 — note
  that explicitly in the log line format (e.g. `identity=anonymous(ip=...)`)
  rather than implying more attribution than you actually have.

**Definition of done**
Click "Show" on a real secret key in the UI → the backend's stdout shows an
audit line for that exact reveal, immediately. Open the Network tab in
browser devtools during the initial ConfigMaps/Secrets page load: the
`GET /api/v1/secrets` response contains no decoded values anywhere, only
after the explicit reveal call does the value appear in a response body.

## Phase 7 — Topology graph

**Goal:** the topology graph is computed from the real cluster graph, for
any namespace, not hard-coded to one `auth`/`keycloak` shape.

**Backend**
- `GET /api/v1/topology?namespace=X` assembles the graph server-side (the
  frontend should never have to guess relationships):
  - Ingress → Service: match `Ingress.spec.rules[].http.paths[].backend.service.name`.
  - Service → Pods: match `Service.spec.selector` labels against Pod labels.
  - Deployment → Pods: match `Deployment.spec.selector` labels directly
    against Pod labels (skip the ReplicaSet hop for simplicity — the more
    "correct" traversal via owner references matters mainly if multiple
    Deployments have overlapping selectors, which is a rare misconfiguration
    worth a code comment rather than upfront complexity).
  - Deployment → ConfigMap/Secret: scan the pod template's
    `envFrom`/`env[].valueFrom`/`volumes` for `ConfigMapRef`/`SecretRef`
    names.
- No new dependency — this is assembly logic over data you already fetch
  elsewhere, not a new K8s API surface.

**Frontend**
- Replace the hard-coded 7-node fixed-position layout in
  `src/app/(shell)/topology/page.tsx` with a real layout, since node count
  and shape now vary per namespace. Start with a **manual layered-column
  layout** (Ingress column → Service column → Deployment column → Pods
  column, with ConfigMap/Secret hanging off the Deployment column) — the
  graph shapes here are constrained enough that this likely covers it
  without a full graph-layout library. Reach for `dagre` or `elkjs` only if
  that turns out insufficient in practice.
- The Topbar's namespace context (currently the decorative "namespace: auth"
  button on this page) becomes real here, at least for Topology.

**New dependencies**
- `go.mod`: none
- `package.json`: none initially; `dagre` or `elkjs` only if the manual
  layout doesn't hold up

**Complexity:** L — mostly on the backend graph-assembly side; the frontend
layout work is medium once the manual-columns approach is chosen.

**Risks to check early**
- None cluster-side. The real risk is scope creep into a generic graph
  library before confirming the simple layered layout is actually
  insufficient — validate with 2–3 real namespaces of varying shape first.

**Definition of done**
Open Topology for the real `auth` namespace: same overall shape as today's
mock (Ingress → Service → Deployment → 2 Pods, Secret/ConfigMap alongside),
but with live pod names and status. Switch to a differently-shaped namespace
(e.g. `default`, with a different Ingress/Service/Deployment count) and
confirm the graph actually reflects that different shape, not a resized
copy of the `auth` layout.

## Phase 8 — Ingress / Gateway API

**Goal:** Network page on real data, with an honest "not installed" state
for Gateway API rather than an empty table or a crash.

**Backend**
- `GET /api/v1/ingresses?namespace=` —
  `clientset.NetworkingV1().Ingresses(ns).List()`.
- `GET /api/v1/gateway-routes?namespace=` — via the Gateway API typed
  client. Detect CRD absence (a `List()` call against an unregistered CRD
  returns a clear "the server could not find the requested resource" /
  discovery error) and respond with
  `{"available": false, "reason": "Gateway API CRDs not installed"}`
  instead of a 500.

**Frontend**
- `NetworkPage` swaps `lib/mock/network.ts` for real fetches; the Gateway
  API tab renders a friendly empty-state message when the backend reports
  `available: false`, instead of an empty `DataTable`.

**New dependencies**
- `go.mod`: `sigs.k8s.io/gateway-api` (typed client for `Gateway`/`HTTPRoute`)
- `package.json`: none

**Complexity:** S/M

**Risks to check early**
- **Check now:** stock k3s/k3d does **not** ship Gateway API CRDs by
  default (Traefik's Gateway API support is opt-in). Confirm this against
  your actual target cluster before assuming the "not installed" path is
  even reachable to test — if it's genuinely never installed anywhere you
  test against, you're validating the happy path only. Either install the
  CRDs on a test cluster or explicitly accept that this path stays
  code-reviewed-but-not-manually-verified for now.

**Definition of done**
Ingress tab matches `kubectl get ingress -A` for real hosts/backends. On a
vanilla k3d cluster with no Gateway API CRDs, the Gateway API tab shows the
"not installed" message — confirming the not-installed path works without
crashing the page.

## Phase 9 — Write actions via GitOps PR (not direct API calls)

**Goal:** Restart/Delete/Rollback buttons are real, and every one of them
ends in an open pull request against the manifests repo — never a direct
write to the cluster. This is AGENTS.md's core rule, implemented.

**Backend**
- New `internal/gitops` package — deliberately **not** `internal/k8s`, and
  it never touches the live cluster clientset for writes. It clones/pulls
  the configured manifests repo, mutates the relevant manifest (e.g. bump a
  `kubectl.kubernetes.io/restartedAt` annotation for "Restart", revert an
  image tag for "Rollback"), commits, pushes a branch, and opens a PR.
- Two-step flow to support the frontend's diff-preview requirement:
  - `POST /api/v1/actions/preview` — computes and returns the diff without
    committing anything.
  - `POST /api/v1/actions/confirm` — takes the previewed change, actually
    commits/pushes/opens the PR.
- New config (extends Phase 0's `internal/config`): `GITOPS_REPO_URL`,
  `GITOPS_TOKEN`, `GITOPS_BASE_BRANCH`. Never log the token.

**Frontend**
- Restart/Delete/Rollback buttons (currently inert `title="TODO..."` stubs
  in `PodDetailPage`/`DeploymentDetailPage`) call `/actions/preview`, open a
  modal showing the returned diff, and on confirm call `/actions/confirm`.
  On success, show a link to the created PR (opens in a new tab).

**New dependencies**
- `go.mod`: `github.com/go-git/go-git/v5` (pure-Go git operations — no
  reliance on a `git` binary being present on the backend host) +
  `github.com/google/go-github/v66` (PR creation via the GitHub API).
  Faster-to-prototype alternative: shell out to the `git`/`gh` CLIs instead
  — fewer Go dependencies, but requires those binaries installed wherever
  the backend runs. Recommend the pure-Go route for anything beyond local
  prototyping.
- `package.json`: none (a plain diff view is enough; a syntax-highlighted
  diff component can be a later polish pass)

**Complexity:** L — the single biggest feature in this plan: git
operations, diff generation for preview, PR creation, and a two-step
preview/confirm UI flow all land together.

**Risks to check early**
- **Needs a real (test) GitOps manifests repo to point at — this doesn't
  exist yet and should be created/chosen before this phase starts**, not
  discovered mid-implementation.
- Credential handling: the GitHub token must never reach the frontend or
  appear in logs — worth a code-review checklist item specifically for
  this phase.

**Definition of done**
Click "Restart" on a real Deployment → preview modal shows the exact
manifest diff (e.g. the `restartedAt` annotation bump) → confirm → a real
PR appears in the configured test manifests repo. The cluster itself is
unchanged until a human (or ArgoCD, post-merge) applies it.

## Phase 10 — Authorization

**Goal:** Keycloak-backed login, with group membership limiting which
namespaces/actions a user can see and do.

**Backend**
- OIDC middleware validating Keycloak-issued tokens —
  `github.com/coreos/go-oidc/v3` for verification; `golang.org/x/oauth2` is
  already pulled in transitively via `client-go`, just needs promoting to a
  direct `go.mod` require.
- Group → namespace/action mapping: read the token's groups/roles claim,
  map to an allow-list of namespaces and permitted actions (config-backed
  for now — e.g. a small YAML/JSON policy file — not over-engineered into a
  full policy engine at this stage).
- Every handler from Phases 1–9 gets a authorization check inserted here —
  this phase touches a lot of existing code, but adds no new endpoints.

**Frontend**
- Login page redirecting to Keycloak (Authorization Code + PKCE), protected
  routes via Next.js middleware checking a session cookie, sign-out.
- Recommend `next-auth`/Auth.js with its generic OIDC provider rather than
  hand-rolling the PKCE flow — first-party Next.js integration.

**New dependencies**
- `go.mod`: `github.com/coreos/go-oidc/v3`
- `package.json`: `next-auth` (v5 / Auth.js)

**Complexity:** L

**Risks to check early**
- This is also where Phase 5's unauthenticated-exec window (flagged above)
  actually closes — explicitly re-verify Terminal access is gated by the
  new per-namespace/action mapping here, not just "logged in = full access
  to everything," which would defeat the point of this phase for exec
  specifically.

**Definition of done**
Opening any Vinaire URL while logged out redirects to Keycloak. Logged in
as a user who only belongs to an `auth-viewers`-style group: Workloads only
shows the `auth` namespace; requests for other namespaces return `403` from
the backend (not just a hidden UI element — the API itself enforces it).

## Phase 11 — Multi-cluster

**Goal:** the Topbar's cluster picker (currently a static "prod-msk-01"
label) is real.

**Backend**
- Config: a named list of kubeconfig contexts (or separate kubeconfig
  files). Per-request cluster selection via an `X-Cluster` header or
  `?cluster=` query param, backed by a small registry
  (`map[string]*kubernetes.Clientset`, and post-Phase-2, per-cluster
  informer factories too — meaningfully more resource-heavy, see risk
  below). New `GET /api/v1/clusters` endpoint listing available contexts.
- No new dependency — `client-go`'s `clientcmd` already supports building
  configs from multiple contexts.

**Frontend**
- Topbar's cluster button becomes a real dropdown sourced from
  `GET /api/v1/clusters`; selection persisted (cookie or `localStorage`)
  and sent as a header on every API call — likely needs a small
  provider/context wrapping `apiFetch` to inject the selected cluster.

**New dependencies**
- `go.mod`: none
- `package.json`: none

**Complexity:** L

**Risks to check early**
- Phase 2's informers multiply per cluster (N clusters × informer
  factories running simultaneously) — decide whether to start informers
  eagerly for every configured cluster or lazily only for the
  currently-selected one(s) before this phase's implementation, since it
  changes the `internal/stream` package's lifecycle model from Phase 2.

**Definition of done**
Configure two kubeconfig contexts (e.g. two local k3d clusters). Switching
the Topbar dropdown reloads Workloads/Dashboard with the other cluster's
real data — no page reload required, no data from the previous cluster
lingering in the tables.
